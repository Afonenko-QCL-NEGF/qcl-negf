# Dupont V843. Сетка и область гамильтониана

Кампания для HTCondor-кластера. Опубликованный опыт выполнен на ревизии
`625e35d24aa0694045febb42a51f1e4006c8cfad` с Julia 1.13.4. Runner через свой
Manifest устанавливает Core `0eba158d21148e0cb3f8c4dae31195aad1f2a43d`.
Научные входы восстанавливаются из Git. Для повтора нужны закреплённый код,
зависимости Julia/Python и локальная конфигурация пула.

## Результаты DAG 95.0

Все 45 расчётных заданий завершились с кодом 0. Финальный узел независимо
прочитал 36 спектров, восемь парных опытов и межплатформенный повтор.
Опубликованные контрольные значения на сетке 144 воспроизведены. Linux и
Windows дали одинаковый статический отказ точки B7, ранг 7, 144 узла.
Максимальная разность энергий составила 1,22 × 10⁻¹⁵ эВ при допуске 10⁻¹⁰ эВ.
Спектральная норма разности взвешенных проекторов составила 1,54 × 10⁻¹⁴
при допуске 10⁻⁸.

На сетках 216 и 288 узлов на период в обоих семействах RMS полного окна
остался ниже 5 мэВ, а RMS решения на одном периоде — выше 5 мэВ. Назначения
состояний сохранились. Наибольшее изменение RMS между двумя сетками
составило 0,5234 мэВ при допуске 1 мэВ. Среди 36 штатных спектров 12 получили
статический отказ, остальные 24 не прошли критерии рисунка. Следующий
транспортный этап по этой матрице не допущен.

## Основная политика выполнения

Перед подачей DAG 95.0 политика ресурсов была изменена. **Основная политика
кампании — одно расчётное задание на машину с выделением всех CPU рабочего
слота HTCondor и фактически доступной памяти в пределах резерва пула.**
Прежняя конфигурация с 2 CPU и 8 ГиБ на задание снята с основной подачи.
Модель, 36 замороженных планов, постановка парных опытов и зарегистрированные
критерии сохранены.

В DAG 95.0 один узел Linux предоставлял 28 логических CPU и 40 ГиБ, шесть
Windows-узлов — по 30 логических CPU и от 19 до 24 ГиБ. На Linux подано 7
работ, на Windows — 38. Один вычислительный поток Julia вызывает BLAS с
числом потоков по выделенному CPU-слоту. Загрузка отдельных фаз зависит от
операций и размеров матриц. [Патч исполнявшегося адаптера](evidence/run-95/worker-site.patch)

## Что измеряем

При 21 кВ/см (75,936 мВ на период), 50 К, k=0 и нулевом Хартри выясняем, сохранится ли различие между двумя операциями при уточнении сетки. Первая операция решает задачу во всём окне и показывает плотности в центральном периоде. Вторая ограничивает H и W тем же периодом **до** диагонализации. Предыдущие опубликованные результаты на 144 узлах дают соответственно 1,185555 и 11,818730 мэВ для PzP, 1,796261 и 11,419264 мэВ для заново построенного базиса Ванье. Это RMS относительных энергий четырёх состояний после одного общего сдвига нуля. Полученный из геометрии базис Ванье имеет статус самостоятельного контроля. [Исходная работа](../v843-spectrum/README.md) · [Критерии и источник оцифровки](../v843-spectrum/admission.toml)

| Ветвь | Задания | Измерение |
| --- | ---: | --- |
| Штатная операция Runner `structure_spectrum` | 36 | Полное произведение окон 7, 9, 11 периодов, рангов 7, 8, 11 и сеток 96, 144, 216, 288 узлов **на период**. Для каждого варианта измеряем три ошибки трансляции, назначения состояний, косинусы плотностей и относительные энергии. Девять точек на 144 узлах связывают новый опыт с опубликованной матрицей. |
| Парное изменение области | 8 | Четыре сетки в каждом из двух семейств. Окно 11 периодов и ранг 11 для PzP; окно 9 периодов и ранг 11 для Ванье. Для каждой пары строятся общие H и W, затем вызываются опубликованные операции Core. Сравниваем внутри семейства: между семействами меняются и локализация, и окно. |
| Межплатформенный контроль | 1 дополнительное | Одна и та же последовательность байтов плана B7, ранг 7, 144 узла на Linux и Windows. Пределы 10⁻¹⁰ эВ по энергиям и 10⁻⁸ по спектральной норме разности взвешенных проекторов, одинаковые причины статического отказа. |

До запуска зарегистрированы следующие правила.

- Если при 216 и 288 узлах RMS полного окна сохраняется в пределах опубликованного порога 5 мэВ, а решение на одном периоде остаётся выше, это свидетельство чувствительности к области. Дополнительно требуем сохранения назначений по форме между сетками внутри каждого варианта и изменения его RMS не более 1 мэВ. Последний допуск выбран для этой кампании как одна пятая порога. Он описывает наблюдаемую устойчивость на двух сетках.
- Если оценки стабилизируются, а прежнее разделение по порогу исчезает, фиксируем, для какой локализации и какой области это произошло. При смене назначений или большем дрейфе получаем неопределённый исход. Для соседних сеток дополнительно оцениваем попарные энергетические интервалы и сходство плотностей на общем координатном интервале. Полная погрешность дискретизации остаётся открытой, в том числе из-за положения гетерограниц относительно узлов.
- Нативные спектры оцениваем в два этапа. Сначала проверяем трансляцию, затем литературные условия. Сверка рисунка для статически отклонённых состояний маркируется как диагностическая. Для прошедших точек проверяем соседние окна одного ранга на одной сетке. Ранг 7 выбран как контроль известного статического отказа, 8 и 11 как контролируемое расширение подпространства.
- На сетке 144 ожидаем прежнюю ошибку 0,162285 при округлении до шести знаков для B7/ранг 7. Для двух парных опытов сверяем RMS с опубликованными значениями в пределах 0,001 мэВ и назначения ролей. Расхождение требует проверки воспроизводимости до интерпретации остальных сеток. Статический допуск отдельной точки подготавливает следующий опыт с операторами транспорта. Ток и стационарность SCBA в этом графе остаются неизмеренными.

## Подача с кластера

На Linux-хосте подачи выберите отдельный каталог с простым абсолютным путём без пробелов. Из чистого клона данной ревизии подготовьте Julia 1.13.4 и Python 3.14 с пакетом анализа. На Windows используйте исходники Git с сохранёнными LF. Рабочие задания получают ZIP с байтами Git и замороженные планы. Сведения об исходных путях, записанные Runner, относятся к хосту подачи.

```sh
julia --startup-file=no --project=runner -e 'using Pkg; Pkg.instantiate()'
python3.14 -m venv .analysis-env
.analysis-env/bin/python -m pip install ./analysis
.analysis-env/bin/python studies/v843-grid-cluster/prepare.py grid-work --freeze
```

С управляющего узла проверьте свободные partitionable-слоты, ОС и память
машин. В приватный JSON-инвентарь включите по одной записи на подходящую
машину. Возьмите `filesystem_domain` из объявления `FileSystemDomain`,
`cpus` — из полного доступного слота, `memory_mib` — из меньшего значения
между памятью слота и доступной памятью ОС, округлённого вниз до ГиБ.
Генератор взвешивает ОС по числу таких машин и распределяет задания внутри
каждой ОС циклически. На полностью Linux-пуле укажите `--linux-only`.
Межплатформенная проверка в таком пакете останется без измерения.

Пример структуры приватного файла:

```json
[
  {"os": "linux", "filesystem_domain": "linux-execute", "cpus": 28, "memory_mib": 40960},
  {"os": "windows", "filesystem_domain": "windows-execute", "cpus": 30, "memory_mib": 20480}
]
```

```sh
.analysis-env/bin/python studies/v843-grid-cluster/dispatch.py prepare grid-work grid-batch \
  --commit HEAD --workers "$WORKER_INVENTORY" \
  --linux-python "$LINUX_PYTHON" --windows-python "$WINDOWS_PYTHON"
```

Проверьте `grid-batch/site-*.sub` по реальным рабочим слотам. Укажите
действительные пути Python и Julia через `executable` и `QCL_JULIA`.
На Windows можно передавать переносимый Python с библиотеками через
`transfer_executable` и `transfer_input_files`. Для готового depot задайте
`JULIA_DEPOT_PATH`. Чтобы установить зависимости из Manifest в рабочем
sandbox, разрешите `QCL_INSTANTIATE=1`. Сверяйте выделение ресурсов и
использование CPU по истории очереди. Инвентарь и пути пула храните на хосте
подачи.

```sh
cd grid-batch
condor_submit_dag campaign.dag
```

Сохраните идентификатор DAG и подтвердите приём очередью. Чат после подачи может завершиться. Независимые попытки пишут в раздельные ZIP, в том числе на Windows. Финальный узел HTCondor возвращает данные в `grid-work`, независимо читает спектры и области и формирует `report/report.md`, `report/native.json` и `report/summary.json`. При сбое остаются журналы, исходные/частичные результаты и перечень отсутствующих измерений. Подробности учёта CPU берутся из истории планировщика. Для итоговой публикации достаточно компактных отчётов, ревизий, хешей и обезличенной квитанции очереди. Сначала проверьте публикуемые поля на локальные пути. Для восстановления итогов после возврата результатов можно повторить `dispatch.py final PACK WORK` на manager в подготовленной среде анализа.
