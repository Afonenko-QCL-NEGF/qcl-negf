# Перенос в Afonenko-QCL-NEGF

Проекты переносятся из `AfonenkoA` в организацию `Afonenko-QCL-NEGF` с прежними именами.
Скрипт `ops/transfer-github.sh` получает состав компонентов из `.gitmodules` текущего checkout,
переносит компоненты первыми, а объединяющий `qcl-negf` — последним. Для текущего графа это
девять репозиториев. GitHub сохраняет их идентификаторы, коммиты, ветки, теги, issues и PR.

Это операция GitHub Transfer через `gh api`, а не создание пустых репозиториев и повторная
публикация. **Не создавайте одноимённые репозитории в новой организации заранее.**

## Подготовка

Нужны Bash 4+, Git, GitHub CLI, права администратора исходных репозиториев и право создавать
репозитории в целевой организации. SSH-ключ используется для Git push. Для API авторизуйте `gh`:

```bash
gh auth status --hostname github.com
# Только если gh ещё не авторизован:
gh auth login --hostname github.com --git-protocol ssh --web
```

Все команды ниже выполняются из корня существующего `qcl-negf`. Если PR с этим документом ещё
не объединён, получите скрипт отдельно, не переключая рабочую ветку:

```bash
gh api --hostname github.com \
  'repos/AfonenkoA/qcl-negf/contents/ops/transfer-github.sh?ref=migration/afonenko-qcl-negf' \
  -H 'Accept: application/vnd.github.raw+json' > /tmp/qcl-negf-transfer.sh
bash /tmp/qcl-negf-transfer.sh --plan --root "$PWD"
```

`--plan` проверяет весь граф до первой операции изменения: целевую организацию, доступ к исходным
репозиториям, наличие занятых имён и идентичность уже перенесённых репозиториев. Ошибки авторизации,
сети и политики не считаются отсутствием репозитория. План не меняет GitHub и локальные remotes.
Право создания репозиториев окончательно проверяет GitHub при выполнении transfer.

## Выполнение

```bash
bash /tmp/qcl-negf-transfer.sh --apply --root "$PWD"
```

После каждого запроса скрипт ожидает завершения переноса и сверяет постоянный repository ID.
После переноса всех проектов он записывает новые локальные адреса: HTTPS для чтения и SSH для
отправки. Незагруженным submodules задаётся URL для последующей инициализации.

Если перенос прервался, сначала повторите `--plan`, затем `--apply`. Уже завершённые переносы
пропускаются. При незавершённом асинхронном запросе проверьте состояние в GitHub перед повтором.
При конфликте имён или чужом repository ID работа прекращается. Скрипт не удаляет репозитории,
не пересоздаёт их, не объединяет PR и не выполняет force push.

## Объединение согласованных PR

1. Завершите перенос всех девяти репозиториев. Новые URL должны существовать до объединения PR.
2. Объедините PR восьми компонентов методом **Create a merge commit**. Корневой PR закрепляет
   точные коммиты этих PR в gitlinks; merge commit сохраняет их в истории `main`.
   Если выбран squash/rebase, сначала обновите gitlinks корневого PR на фактические итоговые коммиты.
3. Проверьте и объедините корневой PR `qcl-negf` последним. Его gitlinks включают все изменения
   компонентов. Версии пакетов и существующие теги `v0.2.0` не изменяются.
4. В чистой локальной рабочей копии обновите объединяющую ветку и компоненты:

```bash
git switch main
git pull --ff-only origin main
git submodule sync --recursive
git submodule update --init --recursive
bash ops/transfer-github.sh --sync-local
git submodule status --recursive
```

`--sync-local` требует, чтобы перенос уже завершился. Он повторно задаёт локальные SSH push URLs,
включая новые клоны submodules. Отслеживаемая `.gitmodules` меняется только через PR; скрипт
не меняет рабочие файлы, gitlinks, ветки и теги. После `git submodule sync` на старой ветке
локальные URL могут снова стать прежними — повторите `--sync-local` после обновления ветки.

Штатные lock-файлы внешних зависимостей сохраняются: перенос не обновляет Python, Julia, npm или
Nixpkgs. Julia `[sources]` указывает новую организацию, сохраняя существующий тег `v0.2.0`.
Исторические коммиты выпуска остаются неизменяемыми и могут содержать прежние URL; GitHub
перенаправляет их на новое расположение, пока старые имена не заняты снова.

## CI и конфигурация площадки

NixOS-модуль runner теперь регистрируется для `Afonenko-QCL-NEGF/qcl-negf`. Обновите приватный
site flake на объединённый коммит и примените конфигурацию CI VM. Проверьте разрешения токена
runner на репозиторий в организации и настройки GitHub Actions/runner groups новой организации.
Приватные site flakes и локальные checkout за пределами этого дерева обновляются отдельно.

Интеграционный workflow запускается при push в `main` и вручную; PR сам по себе не запускает
расчёты на self-hosted runner. После переноса и объединения PR выполните интеграционную проверку.
Для доступа приложения GitHub в чате установите/разрешите его для новой организации.

Первоначальная команда `deno task publish` предназначена для публикации нового выпуска из
подготовленного дистрибутива. Для переноса существующих репозиториев используйте этот скрипт.
