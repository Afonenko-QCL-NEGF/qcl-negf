# Исследовательский процесс QCL-NEGF

Общий репозиторий хранит правила работы агента и интеграционный состав проекта.
Научные постановки принадлежат `qcl-negf-research`, формулы и критерии — ядру,
результаты — неизменяемым артефактам вне Git. Навыки помогают связать эти слои,
но не становятся новым solver, scheduler или источником физических порогов.

## Почему такая организация

Выбран короткий корневой `AGENTS.md` и четыре узких навыка в `.agents/skills`.
Один огромный навык смешивал бы постановку, аудит и выполнение. Копии правил
во всех восьми репозиториях расходились бы. Отдельный обязательный multi-agent
framework добавил бы инфраструктуру до проверки полезности самого процесса.
Навыки работают и с одним агентом; для спорных выводов полезна независимая проверка.

Предыдущие предложенные файлы не считались утверждёнными. Сохранены полезные
идеи — короткое интервью, проверка границ, ограничение дорогих экспериментов —
и заново привязаны к текущим контрактам и источникам. Разговор не доказывает
корректность формулы, а одобрение запроса не означает запуск расчёта.

Научный принцип — сначала установить, что именно измерено и какую физическую
задачу решает код. Итерационная сходимость, достаточность сетки и соответствие
эксперименту требуют разных свидетельств. Методологическое основание:
[Oberkampf & Trucano](https://www.sandia.gov/research/publications/details/verification-and-validation-benchmarks-2007-02-01/).
QCL-специфичные оговорки и источники находятся в
[physics-checks](../.agents/skills/qcl-physics-audit/references/physics-checks.md).

## Один цикл исследования

| Этап | Вход и результат | Условие перехода |
| --- | --- | --- |
| Постановка | Вопрос, альтернативы, наблюдаемые, материалы → brief с критериями и неизвестными | Понятно, какое решение изменит ответ |
| Инвентаризация | Архивы и код → identity, completeness, совместимость reader, пробелы | Доступны свидетельства для конкретных утверждений |
| Аудит | Физика, реализация, результаты и стоимость → таблица доказательств и возражений | Вывод обоснован либо локализован недостающий факт |
| Решение | Сохранить / изменить / измерить / данных недостаточно | Изменение или опыт явно поручен |
| Ограниченный опыт | Зафиксированные plan, budget и stop rules → неизменяемый результат | Бюджет не превышен; результат оценён по исходным критериям |
| Интеграция | Обоснованный diff owning component → PR, затем gitlink общего проекта | Review и проверки соответствуют изменению |

Не все задачи проходят все этапы. Для анализа готовых данных цикл может
закончиться выводом «сохранить код» или точным перечнем недостающих данных.
Нельзя требовать нового запуска только для завершения красивого отчёта.

Для каждого исследования рекомендуется отдельный каталог `studies/<study-id>/`
в `qcl-negf-research`: `brief.md`, `evidence.md`, `decisions.md` и `state.md`.
Это предлагаемая структура будущих исследований, не утверждение о наличии
таких файлов сейчас. `state.md` кратко фиксирует вопрос, выполненное, границы
полномочий, открытые противоречия и следующий шаг; evidence связывает утверждения
с hashes/paths, decisions хранит причины решений и версии критериев.
Не копировать туда HDF5 и историю чата целиком. Машиночитаемые study definitions
и frozen plans остаются действующими источниками параметров.

## Работа несколькими агентами

Координатор задаёт один набор ревизий/артефактов и общий бюджет. При независимых
вопросах можно разделить физическую постановку, численную верификацию,
анализ результатов и стоимость. Делегировать конкретный вопрос и ожидаемый
выход, а не «проведи ещё один полный аудит».

Первичная независимая проверка получает исходные данные без готового диагноза.
После неё сопоставляются предпосылки и свидетельства. Реестр разногласий:
`claim → evidence → objection → discriminating check → decision`.
Количество согласившихся агентов не повышает доказательность само по себе.
Общий код, один источник или общий ошибочный normalizer могут дать общий промах.
Если субагентов нет, использовать последовательные роли с явной оговоркой.

## Производительность как часть исследования

Целевая величина — стоимость получения принятого физического результата:
wall time, core-hours, память и I/O при явно заданной точности. Отдельно считать
затраты неудачных попыток, JIT, диагностики и экспорта. Производительность
одной итерации полезна для локализации, но не заменяет стоимость решения.
Для набора independent runs также оценивать throughput в рамках памяти и очереди.

Результат аудита — ранжированные решения «сохранить / изменить / измерить»
с ожидаемым эффектом, риском для физики, свидетельством и owning component.
При отсутствии фазовых данных нужно предложить минимальную телеметрию,
её стоимость и способ проверить влияние instrumentation. Не переписывать ядро
по одному показателю «выделено 16 CPU, занято 2».
Подробности: [performance skill](../.agents/skills/qcl-performance-audit/SKILL.md).

## Локальный Codex и веб-версия ChatGPT

Каноническая версия правил — принятый commit этого репозитория. В локальном
Codex открыть корень общего checkout с нужными submodules; вызвать один из
`$qcl-research-framing`, `$qcl-physics-audit`, `$qcl-results-analysis`,
`$qcl-performance-audit`. Перед работой попросить перечислить загруженные
инструкции и версии материалов. Отдельный checkout компонента может не видеть
правила родительского superproject: явно предоставить AGENTS и нужный skill.

Codex обнаруживает repo skills в `.agents/skills`; инструкции AGENTS ищутся
по пути от корня проекта. Это описано в официальной документации
[skills](https://learn.chatgpt.com/docs/build-skills) и
[AGENTS.md](https://learn.chatgpt.com/docs/agent-configuration/agents-md).
Проверено 2026-09-28; поддержка конкретного клиента может меняться.

Для веб-ChatGPT прикреплённый `SKILL.md` — доступный текст, но само прикрепление
не доказывает установку навыка и не даёт доступа к локальным HDF5. Предпочитать
поддерживаемую установку skill/plugin; для набора навыков официальный путь
распространения — plugin. Локальные repo skills и workspace/plugin lifecycle
различаются: [официальные границы](https://learn.chatgpt.com/docs/enterprise/skills).
Этот PR не устанавливает личные навыки и не создаёт plugin.

Если установка недоступна, приложить AGENTS, нужный SKILL с его references,
brief/state и компактные доказательства, указав commit и что это инструкции
данной сессии. Не прикреплять все старые версии одновременно и не считать
GitHub connection доказательством автоматического чтения файлов. После merge
обновлять веб-копию из канонической версии, а не редактировать две копии независимо.

Большие архивы удобнее анализировать локально рядом с кодом: один раз сохранить
исходные части, проверить receipts/hashes, читать HDF5 частями, складывать derived
отдельно. В веб передавать постановку, inventory, необходимые slices/таблицы,
графики и ограничения вывода. Локальность снимает необходимость повторно
переносить весь набор в среду анализа; она не означает, что модель работает
offline или что вывод инструментов никогда не передаётся сервису.

## Ближайший практический шаг

После review/merge открыть отдельную задачу: инвентаризация готовых архивов и
аудит доказательности без новых расчётов. Сначала проверить reader/identity,
затем научную пригодность, затем стоимость и пробелы телеметрии. Следующий
эксперимент выбирать по способности различить гипотезы и бюджету.
