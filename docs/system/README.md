# Спецификация следующего релиза QCL-NEGF

Статус: **рабочая спецификация и передача в реализацию**, 2026-10-09. Требования,
подтверждённые пользователем, отделены от предлагаемых решений. Этот корпус
не объявляет функции реализованными и не разрешает вычисления, развёртывание
или удаление инфраструктуры.

[Точка входа в реализацию](implementation-entrypoint.md) содержит первый
проход новой сессии CODEX и prompt для адресного ticket этапа 1.
[Policy ролей и координации](release-roadmap.md#политика-ролей-и-координации)
хранится в roadmap. Корпус `docs/system/` включён в эту версию исходников.
Для fresh clone используйте выбранный опубликованный docs ref с этими
файлами. Подготовка передачи не запускает реализацию.

Цель релиза — получить удобную и воспроизводимую среду стационарного QCL-NEGF
исследования на одном основном сервере и нескольких локальных workers.
Первый обязательный научный рубеж — равновесная стационарная точка
опубликованной GaAs/AlGaAs-структуры при 0 mV/period и 70 K. Полный релиз принимается поэтапно;
его завершение не должно быть условием начала проверки физики.
Оптические gain/absorption спектры отложены до отдельного обоснования
количественного отклика; стационарные transport maps и уровни структуры
остаются в области релиза.

## Порядок чтения

Сначала различить [реализованную baseline](../architecture.md) и целевой
корпус ниже. Для конкретного ticket читать применимые разделы по
[entrypoint](implementation-entrypoint.md), а не весь список подряд.

1. [Требования](requirements.md): согласованный объём, ограничения и приёмка.
2. [Предлагаемая архитектура](architecture.md): система, выведенная из требований.
3. [Сравнение и code review](review.md): фактические расхождения и дефекты кода.
4. [Допустимость и опыт других проектов](feasibility.md): альтернативы,
   контрпримеры, повторное использование инструментов.
5. [Научный рубеж и метод работы](scientific-milestone.md): что именно должно
   обосновывать физический результат.
6. [Порядок рефакторинга и приёмки](release-roadmap.md): зависимости этапов и
   условия перехода.
7. [Чистая пересборка инфраструктуры](rebuild.md): удаление QCL VM, диски,
   подкачка, bootstrap и восстановление; только план.
8. [Физическая документация рядом с исследованием](physics-documentation.md):
   учебный маршрут, source/model cards, Julia docs и локальная публикация.
9. [Результаты и постобработка](results-and-postprocessing.md): опыт BOINC/
   HTCondor/AiiDA, existing NFS publication и конкретные read/derive операции.

Целевой проект выводится из требований и новой архитектуры, затем
сопоставляется с реализацией.
Review не является исходным проектом системы: найденный дефект не должен
автоматически порождать новый сервис, реестр или framework.

## Единственная актуальная версия

Нормативные требования следующего релиза редактируются **в этих файлах**, а
не копируются в новый датированный план после каждого разговора. До принятия
проектных решений их статус остаётся «предложение». После согласования
меняется статус соответствующего решения, а не создаётся вторая спецификация.
Git хранит прежние редакции.

| Материал | Назначение | Правило актуальности |
| --- | --- | --- |
| `docs/system/requirements.md` | Требования и критерии приёмки | Один ID на требование; изменения явно отражаются в review/PR |
| `docs/system/architecture.md` | Целевые границы и интерфейсы | Решения помечены как предложенные или согласованные |
| `docs/system/implementation-entrypoint.md` | Передача новой сессии и первый ticket | Ссылается на corpus/roadmap, не копирует полный release plan или source lock |
| Документация owning component | Реальный публичный API и форматы | Обновляется вместе с реализацией; не копирует общую спецификацию |
| Runbooks | Выполнимые процедуры для выбранного релиза | Указывают предпосылки; не служат журналом сессии |
| `docs/implementation/` | Исторические измерения и проверки | Датированные факты с областью применимости; не доказывают текущий HEAD |
| `docs/superpowers/specs/`, `docs/superpowers/plans/` | Предыдущие проектные материалы | Контекст истории; при расхождении не переопределяют этот корпус |
| Issue/PR и рабочие заметки | Текущая работа, обсуждение, оставшиеся шаги | Не становятся скрытой спецификацией |

У каждого документа компонента при миграции должны быть назначение, статус,
ссылка на нормативный раздел и владелец. Физические формулы и обоснования
живут в ядре/research; их нельзя заменить таблицей требований UI.
Историю не переписываем и существующие журналы не удаляем.

### Миграция документации компонентов

Это перечень owning documentation работ следующего релиза; документы
компонентов не переписаны в этом root-only изменении. Обновлять их отдельными
component PR вместе с действующими интерфейсами, затем root gitlinks.

| Компонент | Текущие точки входа | Что должно стать актуальным контрактом |
| --- | --- | --- |
| Core | `README.md`, theory, examples | Public Julia API, физические assumptions/проверки; expert operators; локальный пример |
| Runner | `README.md`, config schemas, CLI/API docs | Domain request/protocol resolution, persistence/checkpoint, estimate, sweep/continuation status |
| Research | `docs/scientific-inputs.md`, literature, dated fixtures plan | Структура/material/model/protocol отдельно; постановка S01; датированные планы остаются историей |
| Contracts | `README.md`, schemas | Plan/result/attempt locator/status versions и migration; schema не заменяет physics docs |
| Results | `README.md`, `docs/export-budget.md` | NFS reader/brief/full/slices, units/axes, comparison; exports отдельный раздел |
| AiiDA | `docs/service.md`, `docs/deployment.md` | Persisted execution, goal links, budget binding, retry/selection semantics |
| Portal | `README.md` | Пользовательский путь постановки/варианта/графа и API auth; archive recovery отдельно |
| Platform | `docs/bootstrap.md`, `operations.md`, `application-cd.md`, `build-admission.md`, worker docs | Один cold-start/runbook и lifecycle/resource contracts; `status-journal.md` только история |

Runbook должен описывать один поддерживаемый маршрут с entry/exit criteria.
Описание очередного PATH/loader инцидента остаётся в журнале, а в runbook
попадает только итоговый контракт и проверка. Долгосрочные идеи остаются
backlog, не дописываются как обязательные шаги текущего release.

## Правило работы после согласования

Каждая существенная работа связывает `requirement → owning component →
проверяемое изменение → приёмка`. Обновление интерфейса включает контракт,
пример пользователя и миграцию; запись «тесты зелёные» не заменяет описание
проверенного свойства. Component PR публикуется первым, затем обновляется
gitlink интеграционного репозитория.

Полная пошаговая инструкция исполнителю создаётся для принятого этапа,
когда выбраны интерфейсы и бюджет. [Roadmap](release-roadmap.md) сейчас задаёт
порядок и критерии, а не поручение исполнить все работы сразу.
