# Спецификация следующего релиза QCL-NEGF

[Исполнительный план Codex](../implementation/codex-execution-2026-10-27.md)
задаёт запуск на другом ноутбуке: разрешения пользователя, DAG, models/efforts,
read-only оценку старого run без архива и продолжение после ночного обрыва сети.

**Программа от 2026-10-27:** [упрощение проекта на семь дней](../implementation/project-simplification-2026-10-27.md)
объединяет последние решения пользователя, границы API, checkpoint/history,
CI/CD, резидентные VM, процедуры обновления, подключение workers и документацию.
Она заменяет противоречащие ей прежние предложения по совместимости,
эксплуатационному процессу и очередности работ; физическая модель и policy
ролей сохраняются. Статус — проект для review, реализация не запущена.
Перед следующим поручением читать её первой, затем нужные owning contracts.

Статус на **2026-10-19**: единый корпус требований и целевых решений;
исполнение принятого [handoff](../implementation/review-closure-2026-10-19/README.md)
активировано прямым поручением пользователя. [P1](../implementation/review-closure-2026-10-19/operator-permissions.md)
задаёт B/G1/S1 без e–e, а [coordination checkpoint](../implementation/review-closure-2026-10-19/execution/checkpoint.json)
сохраняет отдельную активацию EXEC. Исторические PLAN/approved_standby в handoff
описывают момент его подготовки и не отменяют последнюю команду.

[Dispositions 59 требований](requirement-dispositions-2026-10-19.md) связывают
каждый исходный ID с epoch, источником, текущим scope и решением. Старые «С/Н»
сохранены как документальная история; неизвестные первичные message locators
не объявлены восстановленными. Принятый current scope не требует нового опроса.

Текущие четыре равноприоритетные цели — формализация, документация, ревью кода
и научная приёмка. Исследователь, оператор и разработчик равноправны.
Сквозная цель — задания, позволяющие агенту выполнить конечный проверяемый
цикл без постоянного обращения к человеку. Научная цель — первый физически
осмысленный результат с сопоставлением опубликованному исследованию;
первый контракт теперь выбран в P1/PERM15: стационарное тепловое равновесие
при **0 mV/period и 70 K**, electron–electron = none, с LO/acoustic/impurity/IFR/alloy.
Полный scope включает все findings, подключённый кластер, проверенный worker
distribution с инструкцией, convergence studies и попытку physical acceptance.
Светлая тема и разделение выполнения, сходимости, физических проверок,
дискретизации и валидации сохраняются. Grants не доказывают готовность к
BUILD/OPS/SCI: для каждого зависимого действия нужны technical BIND/READY,
fresh admission и конечные пределы P1; public release согласуется отдельно.

Сведения о прежней передаче ниже читаются по их датам и source identity.

[Точка входа в реализацию](implementation-entrypoint.md) содержит первый
проход новой сессии CODEX и prompt для адресного ticket этапа 1.
[Policy ролей и координации](release-roadmap.md#политика-ролей-и-координации)
хранится в roadmap. Корпус `docs/system/` включён в эту версию исходников.
Для fresh clone используйте выбранный опубликованный docs ref с этими
файлами. Документы передачи сами по себе не активируют исполнение.

Цель среды на одном сервере и локальных workers сохраняется. Датированный
gap RV00 от 2026-10-14 о выборе S01 закрыт P1/PERM15; конечный каталог S1 и
критерии технической готовности заданы [scientific handoff](../implementation/review-closure-2026-10-19/science.md).
Оптические спектры, finite-bias и experimental validation не входят в S1.
Старый наблюдавшийся S01 имеет собственную identity: его raw/provenance
сохраняются, отмена и повторное использование не следуют из новой кампании.
Новый выбранный контракт не доказывает terminal outcome или physical acceptance.

закончить все старые этапы до независимой готовой задачи.

   обосновывать физический результат.
6. [Порядок рефакторинга и приёмки](release-roadmap.md): зависимости этапов и
   условия перехода.

## Актуальность и владельцы документов

Программа общего ревью ведётся в [comprehensive-review.md](comprehensive-review.md).
Requirements сохраняют исходный текст 59 ID; датированные dispositions
фиксируют их текущую применимость после RV00 и P1. Прежняя метка согласования
сама не восстанавливает первичный message locator. Новое решение меняет
disposition с указанием источника; исходная история сохраняется в тексте и Git.
Appendix не создаёт второй полный план или реестр runtime acceptance.
Статусы в таблице — правило ведения материала, а не свидетельство его проверки.

| Материал | Назначение | Правило актуальности |
| --- | --- | --- |
| `docs/system/requirements.md` | Требования и критерии приёмки | Один ID на требование; изменения явно отражаются в review/PR |
| `docs/system/architecture.md` | Целевые границы и интерфейсы | Решения помечены как предложенные или согласованные |
| `docs/system/implementation-entrypoint.md` | Передача новой сессии и первый ticket | Ссылается на corpus/roadmap, не копирует полный release plan или source lock |
| Документация owning component | Реальный публичный API и форматы | Обновляется вместе с реализацией; не копирует общую спецификацию |
| Runbooks | Выполнимые процедуры для выбранного релиза | Указывают предпосылки; не служат журналом сессии |
| `docs/implementation/` | Исторические измерения и проверки | Датированные факты с областью применимости; не доказывают текущий HEAD |
| `docs/superpowers/specs/`, `docs/superpowers/plans/` | Предыдущие проектные материалы | Контекст истории; при расхождении не переопределяют этот корпус |
| Issue/PR и рабочие заметки | Текущая работа, обсуждение, оставшиеся шаги | Не становятся скрытой спецификацией |

У каждого документа компонента при миграции должны быть назначение, статус,
ссылка на нормативный раздел и владелец. Физические формулы и обоснования
живут в ядре/research; их нельзя заменить таблицей требований UI.
Историю не переписываем и существующие журналы не удаляем.

### Миграция документации компонентов

Это перечень owning documentation работ следующего релиза; документы
компонентов не переписаны в этом root-only изменении. Обновлять их отдельными
component PR вместе с действующими интерфейсами, затем root gitlinks.

| Компонент | Текущие точки входа | Что должно стать актуальным контрактом |
| --- | --- | --- |
| Core | `README.md`, theory, examples | Public Julia API, физические assumptions/проверки; expert operators; локальный пример |
| Runner | `README.md`, config schemas, CLI/API docs | Domain request/protocol resolution, persistence/checkpoint, estimate, sweep/continuation status |
| Research | `docs/scientific-inputs.md`, literature, dated fixtures plan | Структура/material/model/protocol отдельно; постановка S01; датированные планы остаются историей |
| Contracts | `README.md`, schemas | Plan/result/attempt locator/status versions и migration; schema не заменяет physics docs |
| Results | `README.md`, `docs/export-budget.md` | NFS reader/brief/full/slices, units/axes, comparison; exports отдельный раздел |
| AiiDA | `docs/service.md`, `docs/deployment.md` | Persisted execution, goal links, budget binding, retry/selection semantics |
| Portal | `README.md` | Пользовательский путь постановки/варианта/графа и API auth; archive recovery отдельно |
| Platform | `docs/bootstrap.md`, `operations.md`, `application-cd.md`, `build-admission.md`, worker docs | Один cold-start/runbook и lifecycle/resource contracts; `status-journal.md` только история |

Runbook должен описывать один поддерживаемый маршрут с entry/exit criteria.
Описание очередного PATH/loader инцидента остаётся в журнале, а в runbook
попадает только итоговый контракт и проверка. Долгосрочные идеи остаются
backlog, не дописываются как обязательные шаги текущего release.

независимые проверки трёх направлений. Новые solver runs, builds, benchmarks,

этому составу исходников и должны проверяться при переносе на другую версию.

## Правило работы после согласования

Каждая существенная работа связывает `requirement → owning component →
проверяемое изменение → приёмка`. Обновление интерфейса включает контракт,
пример пользователя и миграцию; запись «тесты зелёные» не заменяет описание
проверенного свойства. Component PR публикуется первым, затем обновляется
gitlink интеграционного репозитория.

Прежний [roadmap](release-roadmap.md) сохраняет предложенные порядок и
критерии той сессии для перепроверки; он не задаёт автоматическую общую очередь.
После актуализации цели, интерфейсов и бюджета исполнителю передаётся
READY-карточка по [текущему рабочему циклу](agent-review-workflow.md).
