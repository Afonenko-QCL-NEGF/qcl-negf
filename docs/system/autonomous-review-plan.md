# План автономного ревью QCL-NEGF для Codex

> Для агента-координатора: выполняй задания по этому плану и их карточкам.
> При наличии субагентов используй `superpowers:subagent-driven-development`,
> иначе `superpowers:executing-plans`; контракт задания и границы стоимости
> из проекта имеют приоритет. Отмечай выполненные шаги, сохраняй состояние
> и продолжай готовые задачи без повторного согласования обычных действий.

**Цель:** выполнить все направления комплексного ревью, получить проверенные
выводы и задания для обоснованного рефакторинга, обновления документации и
инструкций, а также научной приёмки.

**Архитектура работы:** один координатор ведёт общий журнал, владельцы готовят
отдельные результаты, независимые рецензенты проверяют их по первичным входам.
Формализация, документация, код и научная приёмка имеют равный приоритет;
готовность конкретного входа определяет порядок внутри каждой линии.

**Технологии:** Git и Markdown, штатные инструменты чтения и сотрудничества
Codex; Julia, Python, TypeScript, Nix и HCL рассматриваются в owning компонентах.
Новый сервис координации не требуется.

**Основание:** [программа RV00–RV19](comprehensive-review.md),
[контракт рабочего цикла](agent-review-workflow.md),
[аудит skills и SI01–SI07](skills-and-instructions-review.md),
[метрики M01–M20](review-metrics.md) и
[методика документации](documentation-methodology.md).

## Как начать и что означает выполнение

Запрос подготовить этот план не запускает его. При последующем поручении
«выполни автономное ревью по плану» режим по умолчанию — **review**:
чтение исходников, документов, публичных metadata и ограниченных сохранённых
свидетельств; создание и ведение отчётов/журнала, добавление ссылки на результат
в общий `docs/system/README.md`, проектные решения и конкретные предложения
изменений. Изменение общего индекса ограничено ссылками на результаты прохода;
содержательные правки требований, глав и инструкций остаются patch proposals.
Исполнение тестовых suites, установка среды, builds, benchmarks,
SCBA/Poisson, изменения сервера и реализация продуктового кода — отдельные
этапы с собственными полномочиями и конечным бюджетом. Если такой этап уже
поручен, его разрешение сохраняется: повторно спрашивать его на каждом шаге
не нужно.

Ревью кода и тестов даёт оценку их устройства и доказательной силы; запуск
неизмеренной проверки остаётся отдельным заданием. Задания на docs и skills
дают проверяемые предложения текста/патча. Их внедрение выполняется в
порученном режиме изменений после проверки владельца и сохраняемых свойств.
Вывод «данных недостаточно» завершает анализ объявленного вопроса, но не
подтверждает научный результат или исправность системы.

## Общие ограничения

- Пользовательские цели и последние уточнения действуют; старые «С/Н/П»,
  чаты и roadmap — источники для адресной актуализации, без общей отмены истории.
- Три человеческие роли равны: исследователь, оператор, разработчик.
  Веб-представление всегда светлое, включая ошибки, графики и тёмные настройки ОС.
- Физика и in-memory вычисления принадлежат Core; план/файлы/checkpoint — Runner;
  форматы — Contracts; независимое чтение — Results; постановки — Research;
  execution provenance — AiiDA; ресурсы — Slurm/Platform; представление — Portal.
- Не менять модель, рассеяние, сетку, базис, окно или допуски ради ускорения
  либо сходимости. Не переносить физические формулы и приёмку в scheduler/UI/skill.
- Execution, convergence, physics, discretization и experiment — отдельные
  утверждения. `missing`, `not_measured`, `skipped` и отрицательный результат
  не становятся `pass`. Общий helper не является независимым oracle.
- Gitlinks определяют состав проекта. Не создавать второй ручной revision lock,
  не обновлять submodules до latest и не сбрасывать чужие изменения.
- Исходные массивы, failed logs и архивные identities сохраняются. В публичные
  документы не включать секреты, private inventories или научные массивы.
- Component change публикуется у владельца; root обновляет опубликованный
  gitlink отдельным разрешённым изменением. Merge/deploy не следуют из review.

## Подготовить один проход

- [ ] Прочитать актуальный запрос, root AGENTS, архитектуру и инструкции
  компонентов выбранных задач. Не читать весь корпус вместо адресного входа.
- [ ] Зафиксировать `git rev-parse HEAD`, `git status --short` и
  `git submodule status --recursive`. Назвать этот source **S**. Числа и
  локаторы прежнего аудита на `e48e5b2…` перепроверять на S; не выбирать
  установленную или архивную ревизию по текущему checkout.
- [ ] Отделить dirty текст от HEAD: использовать точную опубликованную версию
  либо сохранить content hash прочитанной копии. При изменении входа закрыть
  старый раунд и создать новую ревизию карточки. Отсутствующий local Git object
  проверять через доступный remote metadata, а не объявлять отсутствующим файлом.
- [ ] Выбрать `campaign` как `<UTC-дата>-<short-root-HEAD>-<номер>`;
  **R** = `docs/implementation/comprehensive-review/<campaign>/`.
  Если проход уже существует, возобновить его только после проверки входов;
  новые источники образуют новый проход со ссылкой на предыдущий.
- [ ] Создать `R/progress.md` и `R/index.md`. Координатор один пишет эти файлы.
  В progress хранить область поручения, source/data binding, остаток бюджета,
  состояния задач, рецензента, последний результат и следующую точную операцию.
  Это журнал свидетельств, не эксплуатационный lock или второй план системы.
- [ ] Разбить каждый RV на пакеты: один вопрос, один owner, ограниченный каталог
  утверждений/границ. Перед назначением записать denominator, входы, разрешённые
  пути, oracle/negative case, проверку, выход и остановку. Неизвестный ответ
  допустим; отсутствующий обязательный вход для выбранной проверки — нет.

Срез опубликованной программы для воспроизводимости этого плана —
root docs ref `193f5bf8700b82e05f7e0f1fdd9c8f3ea0908f07`.
Он не удостоверяет актуальность требований или совпадение его gitlinks с S.
Архивный план/run/attempt сохраняют собственные identity. Точная source map
прежнего чтения находится в [датированном аудите](../implementation/comprehensive-review-source-audit-2026-10-14.md).

## Бюджет и выбор следующей работы

Для будущего режима review по уточнению пользователя установлен предел
**14 часов активного wall time
координатора на весь проход**, включая работу всех агентов и ревью; отдельный
атомарный пакет — до **20 минут**, включая его проверку. Это плановые пределы
для назначения при запуске, а не разрешение вычислительного эксперимента.
Не более трёх одновременно работающих исполнителей, если доступная ёмкость
это позволяет; иначе работать последовательно. Сохранять текущую модель;
effort роли — по применимой policy проекта: авторство `ultra`, аудит/review
`high`, исполнение готового изменения `medium`.

Смена S, новый campaign или возобновление сессии не обнуляют остаток бюджета
одного поручения. Исчерпание фиксируется checkpoint; новый предел не возникает
из повторного создания карточки.

Ограничить показанные extracts пакета 96 KiB, секцию отчёта пакета — 8 KiB;
один RV-отчёт может собирать несколько таких секций. Локальное чтение/разбор
ориентировать на ≤1 CPU и ≤1 GiB рабочей RAM на процесс; это не оценка
ресурсов модели Codex и не профиль solver. Большие source
файлы читать по символам и секциям. Сохранённые metadata сначала оценить по
размеру; не распаковывать массивы по умолчанию. Перед HDF5 slices или иной
постобработкой дополнить карточку RAM/I/O/output пределами. Для любой новой
дорогой проверки нужны точные attempts, CPU/RAM, wall time, I/O/output,
остановка и различающее свидетельство; предел общий для команды. Для уже
порученного bootstrap сохранить CI-once на final ready source ref.

Первый пакет каждой линии: RV00, RV16, RV02, RV08. При трёх слотах четвёртый
начинается, когда освобождается первый. Существующие F01/D01/C01/S01 карточки
из рабочего цикла используются как входные срезы RV00/RV07/RV02/RV08,
их findings не выполнять повторно без новой причины.

Далее выбирать готовый пакет из линии, которая дольше не получала работы;
учитывать конкретный риск и стоимость. Не устраивать общую очередь
«сначала вся наука» или «сначала вся документация». Заблокированный вход
одного пакета оставляет остальные линии доступными.

## Выполнить и проверить пакет

- [ ] Координатор передаёт вопрос, S/архивные входы, owner, пути, критерий,
  бюджет и выход. Исполнитель получает адресный контекст; второй writer
  на тот же путь не назначается. При отсутствии субагентов координатор
  выполняет роли последовательно и обозначает меньшую независимость.
- [ ] Исполнитель проходит карточку, пишет `R/RVxx.md` с sections для пакетов.
  Каждое существенное утверждение содержит commit+path/symbol либо
  artifact hash+dataset/selection. Отдельно записываются observation, inference,
  hypothesis и proposal; выбранные M-ID и `not_measured` имеют явный scope.
- [ ] Независимый reviewer сначала получает вопрос, предпосылки и первичные
  входы без авторского диагноза; затем сопоставляет candidate report с источниками.
  Проверяет отрицательный случай, сохраняемый invariant, достаточность oracle
  и полноту заявленного denominator. Согласие авторов не доказательство.
- [ ] Координатор возвращает воспроизводимые замечания тому же исполнителю.
  До двух исправляющих раундов в остатке общего бюджета; повтор проверки
  обосновывается изменением, failure или открытым свойством. После лимита
  сохранить нерешённое утверждение и наиболее дешёвый различающий шаг.
- [ ] Обновить progress и ссылки index. `done` — все элементы объявленного
  каталога получили проверенный ответ либо точный disposition. Выборка
  остаётся выборкой: если часть каталога не просмотрена, ставить `partial`.
  `needs_data`/`needs_decision` относятся к зависимому действию; `replan` —
  к изменившемуся входу или исчерпанному бюджету.

## Передать результаты в рефакторинг и продолжить после перерыва

- [ ] Каждую находку связать с решением «сохранить / изменить / дополнительно
  измерить / данных недостаточно». Для изменения создать `R/fixes/<RV-ID>-<n>.md`:
  trigger, owner, exact source, permitted paths, сохраняемый contract,
  минимальный patch/design, independent oracle и negative case, точные checks,
  зависимости, полномочия, budget/stop, migration/docs и критерий закрытия.
- [ ] Если контракта или входа не хватает, создать конечную discovery/design
  карточку вместо произвольного рефакторинга. READY implementation требует
  известного invariant, воспроизводимого check и разрешённого этапа.
  Не придумывать будущие API или ослаблять tolerance, чтобы сделать карточку READY.
- [ ] При порученном изменении: isolated owning checkout → patch → targeted
  checks → независимое review → component PR → опубликованный root gitlink.
  Публикация следует уже данному поручению; local finding не превращается
  автоматически в GitHub comment, merge или deploy.
- [ ] Свести `R/index.md` по четырём целям и трём ролям; добавить source views,
  findings, docs/skills proposals, criteria/gaps, M-ID coverage и fix queue.
  Координатор добавляет в общий `docs/system/README.md` ссылку на этот результат,
  без копирования формул и массивов; это разрешённое действие режима review.
  Старые отчёты остаются со старой identity.
- [ ] При завершении сессии сохранить следующую точную операцию и остаток
  бюджета в progress. Новый проход сначала читает этот checkpoint и проверяет
  входы; не повторяет принятые checks без причины. План не создаёт фоновый
  запуск: продолжение требует активного исполнения Codex.
