# Запуск переработки кластера и научного приложения

Новая программа от15ноября2026. Основные документы:
[план](clean-start-plan-2026-11-15.md) и
[карта прежних требований/функций](functional-reassessment-2026-11-15.md).
Публикация не запускает установку или удаление. Ручной старт пользователя в новой
сессии на ноутбуке с доступом к LAN/Proxmox активирует поручение ниже.

## Цель и первая контрольная точка

Получить простой рабочий кластер на HTCondor и согласованное научное приложение,
очистив старый QCL и лишние механизмы. Proxmox сохраняется. Первый pool:
CachyOS host worker без дополнительной VM и Linux guest прежнего Intel Xeon PVE.
Windows native — следующий этап. Исходная точка назначения репозиториев: Core и
одно приложение с Runner/analysis/studies/lab; конкретная научная база определяется свежим кодом.

Стартовый промпт задаёт **первый автономный инженерный этап до12часов** с ручного
старта; контрольная точка наступает раньше, если первый результат получен либо
продолжение требует нового решения. Это новый инженерный этап, не наследование
срока научной кампании133. Последние30минут оставить на завершение текущих действий,
сохранение состояния и отчёт; новых тяжёлых работ в это время не начинать.
Продолжение после контрольной точки обсуждается отдельно, без автоматических расписаний.

Первый результат: два Linux worker одной очереди, job из CLI и GUI, outputs,
наблюдаемая cancel, совместное размещение, графический мониторинг и машинные доступы.
Самостоятельная Julia/Pkg проверка среды выполнена. Это инженерный результат;
он не означает сходимость SCBA/Poisson и не требует завершения Windows/UI редактора.

## Полномочия после ручного старта

В пределах согласованного плана разрешены без повторного подтверждения:

- Чтение и изменение owning source/docs/tests; ветки и PR; merge существенных
  изменений после независимого review и относящихся к ним проверок. Старые PR не сливать оптом.
- Native live inventory, установка/настройка системных пакетов, HTCondor,
  Julia/Pkg, Ansible, выбранного готового GUI/monitor; инженерные пробы, сборки,
  исправления и deployment на принадлежащих QCL ресурсах.
- Остановка и удаление подтверждённых старых QCL VM/jobs/results/checkpoints,
  AiiDA/Slurm/NFS/releases и связанных остатков прежнего контура на старом Xeon PVE.
  Не нужны старый data backup, migration, R00 или backwards compatibility.
- Перенос полезного содержимого репозиториев и вывод ненужных после извлечения
  актуального кода, литературы, нужных научных refs и завершения их использования
  активной кампанией. Нужное новое содержимое сначала доступно по новому месту.

Обязательно сохраняются гипервизор, foreign VM/jobs/shared storage, administrative
network/access и машинные credentials. Независимая Julia VM и вся научная кампания133
на другом host исключены из очистки. Неизвестное владение требует выяснения до
разрушающего действия; это не повод остановить независимые работы.

Это инженерное поручение. Короткие численные проверки входов/state/producer-reader
допустимы с явными конечными CPU/RAM/time/output bounds. Новая автономная физическая
кампания, изменение модели/допусков ради работоспособности и отмена чужого исследования
не входят в этот старт. Используй synthetic/tiny fixtures для инженерных вопросов;
реальный научный маршрут проверяй отдельно на разрешённой постановке, без заявления о сходимости.

## Начало на целевом ноутбуке

1. Открой отдельный чистый checkout опубликованной ветки
   `codex/cluster-clean-start-2026-11-15` репозитория
   `Afonenko-QCL-NEGF/qcl-negf`. Проверь фактический HEAD/status/submodules;
   не переноси dirty overlay другого checkout и не выполняй старый bootstrap из README.
   Публичная ветка содержит инструкции поверх исторического main, а не готовый новый runtime.
2. Прочитай новые AGENTS, этот вход и план. Карта функций нужна для выбора
   поведения; 451PR/все старые чаты заново читать не требуется. Старые компонентные
   deployment/CI/skills правила — объекты пересмотра, научные требования сохраняются.
3. Проверь текущую133 и handoff параллельной сессии, актуальные refs/PR/незавершённые
   изменения Core/Runner. Обнови изменившиеся части карты. Не выбирай окончательную
   базу по сегодняшним gitlinks и не объявляй текущие ограничения вечными.
4. Если научная работа продолжается, готовь инфраструктуру независимо; её code
   cleanup/перенос дождётся handoff либо явного согласования владения. Нет необходимости
   останавливать её или ждать её окончания для запуска инженерного pool.
5. Найди существующие private inventory/SSH/config/credential references на этом
   ноутбуке. Пароли/ключи не публикуй. Сними actual PVE VMID/storage/config/status;
   отдели старый QCL от foreign объектов и составь конкретный список удалить/оставить.
   Проверка списка устанавливает принадлежность, не запрашивает уже данное разрешение повторно.
6. До очистки проверь практический путь установки HTCondor на CachyOS и готовых
   пакетов Linux guest. При несовместимости решай конкретный вопрос; не создавай
   свою package factory. CPU/RAM берутся по свежим фактам после reserves гипервизора
   и остальных VM; плановая сборка ждёт завершения jobs выбранного host.

Дальше выполняй последовательность основного плана. Обновление общего runtime
выполняется в обслуживание после завершения его jobs. После потери связи проверь
native состояние до повтора; ручная сверка допустима. Доступы и private state не
должны зависеть от работоспособности научного GUI.

## Научное приложение после handoff

По фактическому свежему коду выбери целостный input/resolver → execution → state
writer/reader → analysis путь. Убери ненужные дубли, брошенные options/branches и
private imports; нужные partial connections доведи. Сохрани reference/oracle,
численные варианты, units/weights/signs, residual history, результаты и решения кампании.
Не удаляй extension/adapter implementation по виду пустого generic объявления.

Зафиксируй судьбу всех семейств из карты: поддерживается сейчас, следующий этап,
исследовательская идея либо удалено как ненужный механизм. Конфигуратор, структура,
basis preview, used-input help, plots/compare и минимальная карточка исследования
не должны исчезнуть молча. Это не требует переписать весь прежний Portal до первого job.

Проверь один настоящий научный путь от входа до независимого чтения и отчёта,
затем необходимые для долгой работы pause/checkpoint/restart и seq/concurrent
throughput. Численная сходимость, физические проверки и acceptance остаются отдельными.
Старые архивные форматы и общий release/version/proof framework не восстанавливаются.

## Работа и отчёт

Sol/high ведёт; другой Sol/high независимо проверяет существенную дельту и
необходимость новых abstractions; Sol/xhigh — конечный сложный вопрос; Terra —
ограниченная механика. Используй штатных subagents. Навыки пересматривай по пользе,
а не применяй автоматически. Не меняй глобальные настройки моделей или доступов.

Не добавляй CI-доставку по собственным SSH-скриптам, resource broker, receipt/
admission/reconciliation service, второй package manager и бесконечный agent loop.
Обычные JobID/status, системные пакеты, Pkg, Ansible и ручные действия достаточны
до появления конкретной повторяющейся проблемы.

В контрольной точке сообщи: что реально работает для пользователя; ссылки на PR;
выбранные фактические scientific refs; что очищено и сохранено; состояние machines/
jobs/results; выполненные проверки и ограничения; один следующий шаг. Не заменяй
готовность количеством тестов, commits или процентом по документации.
