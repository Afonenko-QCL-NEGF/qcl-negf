## State transitions и source ownership

L1. `ops/application_release.py::lifecycle_owner` держит nonblocking EX flock на `runtime/delivery.lock`; `deliver_pool`, `deliver_cli` повторяют authority/guard внутри owner. `ops/worker_lifecycle.py::shutdown_step` держит per-node lock; `_shutdown_owned_poll` берёт общий owner только для capture/finalize, Runner pause/verify-stop выполняются вне общего owner, с durable intent. `startup` берёт тот же delivery lock целиком. Это локальный flock, не распределённая lease: kernel release при смерти процесса не заменяет persisted reconciliation.

**Source gap L1:** `ops/application_release.py::main`, строки 1444–1463, выдаёт standalone `prepare-initial`/`activate` другой `activation.lock`; controller activation не вызывает `lifecycle_guard`. Например, matching closed gate + существующий `cluster-update.json` разрешают controller `activate`, хотя delivery/startup/shutdown видят update как unknown и блокируются. Это второй публичный путь записи profiles/allowlist/env/ready и restart controller units вне общего owner. Сам remote child activate нужен для owned delivery; простая замена lock создаст deadlock между parent delivery и его SSH child. Поэтому требование «единственный writer» пока не доказано, нужен explicit parent/child ownership contract; [ticket RV06-01](fixes/RV06-01-controller-activation-ownership.md). Live concurrent transition не измерялся.

L2. Desired identity — `manifest` release_id/application_path/solver_executable; observed health — `check`, node envelope и ready. `activate` удаляет прежний release.json, проверяет closures, устанавливает два profiles; controller регистрирует Code UUID, публикует allowlist; затем env, ready=false, start/restart, is-active и pinned solver self-check, только потом ready=true. `guard` требует open=true и exact release_id/runtime ready/solver. Crash до final ready обычно даёт missing/false runtime и closed shared gate у owned fleet delivery. `publish` делает tempfile→file fsync→replace→parent fsync; **удаление старого ready не fsync**, и профили/allowlist/env/record не составляют одну filesystem transaction. Исходник не доказывает power-loss atomicity всей последовательности; gate+exact identity являются дополнительным барьером, а live power-loss остаётся not_measured.

L3. `unresolved_deliveries` блокирует admission-intent, requires_reconciliation и running pending mutation; `lifecycle_guard` не очищает их и блокирует любой `cluster-update.json`. `_deliver_cli_locked::checkpoint` пишет приватный attempt UUID receipt и отдельный intent перед open publication, общий delivery-report — лишь публичный summary. `_deliver_pool_owned` закрывает gate до quiesce, требует verified envelope от каждого selected node, rechecks authority до admit/open. `close_after_failure` отдельно пытается закрыть gate: если это не удалось, open=None/admission_state=unknown/critical_admission_failure=true, а не предполагаемый успех. Собственный intent удаляется лишь последним fallible success действием; несинхронизированное удаление может консервативно вернуться после crash. Автоматического trusted reconciliation или I14 update adapter здесь нет.

L4. `_shutdown_owned_poll` сохраняет capture_pending **до** DRAIN; объединяет persisted и active descriptors, требует scoped Runner pause+verify-stop. Исчезнувший из squeue job удаляется из pending лишь если он verified и отсутствует при final reread. Ошибка capture/finalize сохраняет reconciliation_required. `validate_shutdown_intent` запрещает safe_to_power_off при unknown/incomplete scope; empty queue не доказывает stop receipt.

L5. `startup` проверяет enrolled same machine/new boot, authorizes event, сохраняет returning до мутации, DRAIN/queue-empty, closure copy, activate/check envelope, identity rechecks. Перед RESUME пишет независимый admission-intent и pending_action=resume; terminal resumed state сохраняет ownership event, только собственный marker снимается последним. Failure после mutation оставляет reconciliation и попытку gate-close; claimed failure закрытия — unknown. Startup не выполняет recovery research submission.

L6. `prepare_initial` разрешает missing gate лишь cold initial controller без existing record/env; worker missing gate отказывает. Matching closed release обязательна, gate bytes reread после closure checks; существующие exact ready/Code/provenance сохраняются. `guard` отклоняет stale worker/job pin; `node_check` разрешает prepared selected release при closed gate, но job guard остаётся отдельным барьером.

L7. `ops/bootstrap_build.py::validate_preflight/main` требует ровно четыре role drv paths и strict validated nginx target, пишет exclusive mode0600 receipt; evaluation-only не объявляет nginx test измеренным. Это **не build admission owner**: свежий resource snapshot проверяет `ops/build_admission.py::admit` (captured_at в MAX_AGE_SECONDS, complete inventory, idle builders, empty read queue либо оба scientific roles absent, CPU/RAM reserves). Это policy decision, не ресурсная reservation. Frozen root deployment §§«Preflight», «Сохранение попытки и приёмка» дополнительно требует original failed receipts и разделяет engineering/services/restore/final CI/science.
