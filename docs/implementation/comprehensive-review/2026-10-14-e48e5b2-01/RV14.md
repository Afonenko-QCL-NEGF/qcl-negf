## Точные finding/negative cases

**Наблюдение F14.1:** direct Portal wheel build hook принимает существующие index.html и *.js,
не сравнивает content с current frontend/package-lock. Path/symbol Portal
`10b6c871bb89cce4f2bdc1c4cdaa91e500111ceb:hatch_build.py::CustomBuildHook.initialize`.
**Вывод:** guard доказывает наличие browser assets, а не их source freshness. Это относится
к standalone packaging; root release специально вызывает frontendBuild, Nix derivation
строит source separately, поэтому им не приписывается установленная регрессия.
**Hypothesis:** оставленный старый static payload мог бы попасть в direct wheel.
Этот negative case здесь не исполнялся. **Proposal:** owning documentation должна точно
описать поддерживаемый wheel build workflow; design определить, требуется ли stronger
source-stamp guard для direct build. Не вводить ещё один maintained revision lock.

**Наблюдение F14.2:** Runner standalone `[sources]` Core v0.2.0 и workspace post-tag Git link
сохраняют one version string. **Вывод:** ownership/import report обязателен перед переносом
test receipt. Наличие разных resolution routes само не bug; отдельные reproducible packaging
checks должны выбирать маршрут. Reference/optimized agreement с общими helpers не научный oracle.

**Negative case F14.3:** новый root HEAD при неизменившихся некоторых component hashes
не наследует full-release accepted. `ops/application_cd.ts` включает весь derived source graph
в release_id, однако scientific and CI acceptance являются отдельными receipts, а не hash facts.
Saved RV01 scientific=false/full-release-CI=false сохраняется.
