# Очистка QCL и устройство нового этапа


## Уточнения пользователя при исполнении 17 ноября

Этап запущен вручную 17 ноября; текущее окно — до 22:00 Europe/Minsk.
После первого инфраструктурного опыта VM описываются OpenTofu, внутреннее
окружение — Ansible. Нужны переносимые заготовки Ubuntu и Windows workers
для других принадлежащих пользователю серверов LAN. Первые заготовки находятся
в [lab](../../lab/README.md); source validation отличается от реального deploy.
Существующую VM принимают в OpenTofu через обычный import и просмотр drift;
её не пересоздают ради соответствия новому описанию.

Общее правило инструментов: по умолчанию принимать системную установку без
точного version gate; при отсутствии системной — устанавливать актуальный
стабильный upstream штатным способом. Для текущего опыта отдельно запрошен
HTCondor 26+. Номер фактически проверенной версии — свидетельство, а не
постоянный pin или список разрешённых артефактов. Собственный механизм
подтверждений, хеширования, допуска и reconciliation не создавать.
Научный Pkg Manifest описывает зависимости конкретного проекта и сохраняется.
Обновление общего runtime выполняется при свободном worker.

Обычный запуск не должен требовать выбора сервера и ручного ввода CPU/RAM.
Приложение формирует разумные defaults и оценку ресурсов по постановке;
HTCondor размещает задания и заполняет свободные partitionable slots после
резервов хоста. Явное переопределение ресурсов остаётся дополнительной настройкой.
Julia/BLAS threads согласуются с выделенными CPU. Серия независимых расчётов
распределяется между workers; ускорение одиночного solve ограничено его
фактическим параллелизмом. Этот договор требует проверки научного пути Runner,
а не только инженерного shell payload.

Конечный GUI должен поддерживать привычные сценарии научного проектирования:
слева дерево проекта, в центре настройки с единицами/help, справа preview/plots,
снизу очередь/невязки/журнал; постоянные действия открыть/сохранить/проверить/
запустить/остановить. Сохраняются расположение панелей, параметры графиков,
исследования, сравнение и повторное открытие результатов. Ориентиры —
[компоновка COMSOL Desktop](https://www.comsol.com/support/learning-center/course/how-to-navigate-the-comsol-multiphysics-user-interface-12/personalize-the-comsol-desktop-34391)
и [рабочий процесс nextnanomat](https://www.nextnano.com/tools/nextnanomat.php).
Это требования к целевому приложению; установленный Open OnDemand сам по себе
не является реализацией научного конфигуратора и анализа.

План от 15 ноября 2026 года. Учитывает полный отказ от совместимости с прежним QCL, обязательные GUI запусков и мониторинга, сохранение машинных доступов. Исполнение будет в отдельной сессии на CachyOS-ноутбуке с доступом к LAN и Proxmox. Этот документ не запускает удаление, установку или новую научную кампанию.

**Предлагаемая цель — два репозитория и один готовый планировщик.** Численный Core остаётся самостоятельным; Core и Runner проходят очистку дублей, брошенных ветвей и незавершённых соединений по актуальному состоянию при старте. Runner, анализ, постановки и небольшую конфигурацию лаборатории собираем в приложение. Первый кластер — worker непосредственно на CachyOS host и Linux worker на очищенном прежнем Intel Xeon Proxmox. Отдельная worker VM на ноутбуке не нужна. Windows VM подключается следующим этапом. Базовый кандидат очереди — HTCondor; готовый GUI запусков — Open OnDemand. История фактических ресурсов предоставляется отдельным небольшим готовым средством мониторинга.

**Главный принцип — максимальная простота и работа над физикой.** Очередь, размещение, перенос файлов и повторный запуск принадлежат HTCondor; зависимости и кеши — Julia Pkg; установка и обновление служб — обычным пакетам и короткой Ansible-конфигурации. Редкие неисправности допускают ручное исправление по короткой инструкции. Собственные менеджеры пакетов, SHA-допуски к запуску, receipts, автоматический ремонт и согласование состояний нескольких систем в новый состав не входят. Новая автоматика появляется только для конкретной повторяющейся проблемы, которую неудобно решать штатными средствами.

## Готовность к реализации

Архитектурное направление определено. По дополнительному требованию пользователя выполнена [сводная сверка функций, требований и свидетельств](functional-reassessment-2026-11-15.md): первый вариант плана был неполон в части научного приложения. Эта карта сохраняет важные возможности и идеи, включая частичные реализации; она не объявляет весь старый код готовым и не замораживает будущую базу.

**При запуске реализации нужна свежая ревизия Core/Runner и результатов параллельной научной сессии.** На этой базе выбираются согласованный рабочий путь и судьба конкретных реализаций. Обновляются изменившиеся участки карты, без повторения всей истории. Пока научная сессия меняет код, инфраструктурная подготовка независима; cleanup/перенос её научного кода ждёт handoff либо явного согласования владения. Installation details, фактическая нагрузка и работа интерфейсов проверяются в ходе реализации.

Передача подготовлена в отдельной ветке `codex/cluster-clean-start-2026-11-15`:
новые AGENTS, [точка входа исполнения](cluster-execution-2026-11-15.md), этот план и
карта функций. Ручной старт в новой сессии активирует первый инженерный этап до12часов,
затем контрольная точка; публикация сама по себе ничего не запускает. Старые
R00/P01–P32, Superpowers, Nix/AiiDA/Slurm release-программы не являются продолжением
этого этапа. Существующие unrelated изменения сохраняются; новый исполнитель не
накладывает старый dirty overlay.

Первый рабочий результат: оба Linux worker принимают задания одной очереди; простой payload запускается из CLI и GUI, виден в мониторинге и возвращает outputs; проверены отмена и одновременное исполнение; машинные доступы работают. Самостоятельная проверка Julia/Pkg подтверждает пригодность среды. Это достаточная инженерная база для подключения научного приложения. Windows, развитый каталог и все возможные графики не блокируют этот результат. Реальная научная приёмка и проверка numerical resume остаются следующими работами на актуальном solver.

## Принятые границы очистки

- Старые QCL-VM, их данные, checkpoints, NFS dataset, AiiDA/PostgreSQL и releases можно удалить. Backup, миграция DB, чтение старых форматов и совместимость прежних API не являются условиями нового этапа.
- Proxmox, посторонние VM и общие ресурсы хоста сохраняются. «Под ноль» относится к прежнему QCL-контуру.
- Активная научная кампания [#133](https://github.com/Afonenko-QCL-NEGF/qcl-negf/issues/133) находится на другом хосте. Её машина, новые данные и незавершённые изменения сохраняются. Перенос/удаление используемых ею репозиториев выполняется после передачи её результатов.
- Машинные credentials, SSH keys/agent/config, known_hosts, доступ к Proxmox и существующее приватное хранилище доступов сохраняются. Устаревшие сервисные секреты QCL отделяются от машинных доступов перед удалением.
- В этой сессии выполняются аудит и планирование. Клиенты удалённого доступа пока не выбираются.

## Как изменится инфраструктура

| Сейчас в исходниках прежнего контура | Предлагаемый новый состав |
| --- | --- |
| Отдельные роли storage/control/compute/CI, Nix images и собственное переключение releases | Один Linux guest на Proxmox с управляющими службами и worker; CachyOS host — второй worker. Отдельную build VM создавать только при доказанной необходимости |
| Portal → AiiDA WorkChains → Slurm → Runner | Open OnDemand либо штатный CLI/API → HTCondor → Runner |
| Собственные admission, enrollment, memory grants, receipts и release reconciliation | Штатная очередь и стандартные Ansible tasks; небольшие submit/launcher templates |
| NFS как обязательная часть пути всех исполнителей | Локальный scratch и штатный transfer HTCondor; устойчивый каталог новых результатов на Proxmox storage |
| Сборка и запуск связаны с Nix/Deno factory | Официальная Julia, штатный Pkg; Python/uv только для нужного анализа и интерфейсов |
| Обязательное согласование множества VM ресурсов | Достаточно крупная worker VM, несколько jobs внутри неё; build после завершения текущих jobs на выбранном хосте |

Все GUI и служебные данные не требуют отдельных VM по числу продуктов. На первом этапе управляющие службы можно совместить в одном Linux guest с резервом ресурсов. Сам гипервизор не становится местом установки научного приложения. Новая VM использует обычную доступную сеть Proxmox; прежняя собственная маршрутизация между ролями не переносится автоматически.

Для новых Linux guests предлагается Debian stable из поддерживаемой линейки выбранных пакетов. У OOD есть официальные инструкции установки для Debian 12/13; сам факт наличия пакетов не проверяет настройку нашего GUI. CachyOS host сохраняется. Способ установки HTCondor на CachyOS проверяется в начале первого рабочего этапа, до очистки старого контура: поддержка Julia на Linux не гарантирует готовый scheduler package на конкретном rolling distribution. Windows native остаётся целью подключения, но Linux пилот не ждёт Windows-порта. [OOD installation](https://osc.github.io/ood-documentation/latest/installation/install-software.html).

HTCondor имеет native Windows distribution, штатный transfer и разделение узла между jobs. OOD имеет официальный HTCondor adapter, но Windows launcher по умолчанию не готов: его стандартный executable — `/bin/bash`. Первый Linux launcher и последующий Windows template проверяются как конфигурация готовой очереди. [HTCondor Windows](https://htcondor.readthedocs.io/en/v26_0-branch/platform-specific/microsoft-windows.html), [file transfer](https://htcondor.readthedocs.io/en/26.x/users-manual/file-transfer.html), [OOD adapter](https://osc.github.io/ood_core/OodCore/Job/Adapters/HTCondor.html).

## GUI и машинные доступы входят в результат

| Возможность | Требуемое поведение | Основа |
| --- | --- | --- |
| GUI заданий | Выбор входа и ресурсов, submit, очередь, состояние, отмена, logs и ссылки на outputs | OOD Project Manager + HTCondor adapter |
| Кодовый доступ | Те же входы, очередь и результаты; job из GUI виден CLI и наоборот | Native HTCondor CLI/API |
| Ресурсный мониторинг | История фактических CPU/RAM/swap/disk/network на узлах; отдельно видны доступность и заявленные ресурсы очереди | Первый кандидат — Beszel; Netdata — резерв при потребности в более подробной диагностике |
| Результаты | HDF5 slices с осями/единицами и научные reports; process completion отдельно от сходимости | Независимый reader + JupyterLab/H5Web |
| Управление машинами | Доступы по SSH, RDP, VNC; HTTPS к Proxmox и web UI | Нативные клиенты будут выбраны позже; браузерный remote-access gateway не требуется |

Мониторинг узла не является per-job accounting. Нужны оба уровня: запас ресурсов самого Proxmox host и фактическая нагрузка внутри worker guest. Связь с JobID и стоимость конкретного solver берутся из HTCondor и Runner, когда соответствующие измерения действительно есть. Нельзя выдать общий график VM за память отдельного расчёта.

Beszel предлагает один hub и native agents, включая Windows; он не ограничивает ресурсы и не предоставляет SSH/RDP/VNC. Retention подробной истории и принудительное светлое оформление ещё не проверены. Установить сразу Beszel, Netdata и Prometheus/Grafana не предлагается. [Beszel metrics](https://beszel.dev/guide/what-is-beszel), [native agents](https://beszel.dev/guide/agent-installation), [Netdata Windows](https://learn.netdata.cloud/docs/netdata-agent/installation/windows).

Все web UI, графики и терминалы новой системы должны быть светлыми. Default Light не считается доказанным запретом автоматической тёмной темы. Настройка проверяется на фактически выбранных версиях.

Приватный список подключений должен содержать машину/роль, адрес, протокол, порт, пользователя, ссылку на credential, SSH host key либо другой применимый trust record. Секретные значения не входят в публичный Git. Существующий способ хранения сначала инвентаризируется на целевом ноутбуке; новый password manager или единый auth server здесь не назначается. Доступ Codex по SSH и доступ человека через выбранные клиенты используют согласованные машинные записи.

Scientific GUI использует штатную аутентификацию и понятную область доступа к jobs/results выбранного пользователя/доверенной группы. Смена выбранного run или входа делает прежний ожидающий ответ неактуальным; UI не показывает его как результат нового выбора. Pending, error и unknown сообщаются явно. Для этого не нужен новый IAM, token issuer или actor framework.

VNC консоль Proxmox и обычный VNC server внутри гостя — разные endpoints. Прямой административный HTTPS доступ к Proxmox сохраняется независимо от работоспособности нового приложения. Пересозданный Linux guest получает собственную SSH identity; trust обновляется адресно.

## Девять репозиториев превращаются в два

| Репозиторий | Целевая судьба | Сохраняемая ответственность |
| --- | --- | --- |
| `QCLNEGF.jl` | Сохранить самостоятельным | Физика, typed parameters, in-memory solver, reference/optimized numerics и научные oracles |
| `qcl-negf` | Превратить из superproject в приложение | Runner/CLI, новые formats, reader/reports, studies, lab config, инструкции и короткий CI |
| `QCLNEGFRunner.jl` | Перенести полезный пакет в приложение после handoff кампании; отдельный repo упразднить | Прямой запуск, inputs, checkpoint, запись массивов и отчётов; OS adapter |
| `qcl-negf-contracts` | Перенести необходимый минимум, repo упразднить | Один новый формат входов/outputs и его проверка, без отдельного release lifecycle |
| `qcl-negf-results` | Перенести полезные reader/математику, repo упразднить | Независимое чтение, научные диагностики и manufactured oracles |
| `qcl-negf-research` | Перенести полезные inputs/literature, repo упразднить | Постановки, hypotheses, параметры и ссылки на источники |
| `qcl-negf-aiida` | Удалить из нового состава; repo кандидат на удаление | Его workflow/ORM/plugin API не переносится |
| `qcl-negf-portal` | Удалить старое приложение; repo кандидат на удаление | Готовый GUI заменяет lifecycle/backend; полезные научные представления извлекаются выборочно |
| `qcl-negf-platform` | Сохранить лишь нужную конфигурацию в приложении; repo упразднить | Новые Ansible/HTCondor/OOD/monitoring config вместо старого deployment framework |

Целевая структура приложения:

```text
qcl-negf/
  runner/       Julia package и основная среда запуска
  analysis/     независимый reader и отчёты
  studies/      входы, постановки и литература
  lab/          Ansible, HTCondor, OOD, выбранный monitoring
  docs/         актуальное устройство и способы работы
```

Core подключается штатным Julia Pkg; отдельный superproject и восемь gitlinks больше не нужны. Точные зависимости фиксирует native environment, точные исходники опыта — запись запуска. Не вводить вручную синхронизируемый revision registry. Папки и модули сохраняют ответственность без обязательных отдельных repositories и общего semver.

Семь выводимых репозиториев можно удалить после извлечения полезного содержимого и завершения работы активной научной кампании с их refs. Обязательного долгосрочного archive или слоя deprecated API нет. Открытые научные изменения адресно просматриваются перед переносом; старые интеграционные PR не сливаются оптом ради закрытия очереди.

## Что меняется в коде

**Сохранять по смыслу:** численные операторы и независимые oracles; прямой Runner; чтение scientific input; checkpoint полезного текущего пути; запись исходных массивов; bounded HDF5 reader; meaningful diagnostics. Сохраняемый численный код продолжает научную проверку — выбор Core не является заявлением о доказанной сходимости.

**Переработать:** границу Runner/OS/очереди, минимальный input/output contract, discovery Julia executable, измерение ресурсов и переносимую telemetry. Scheduler передаёт обычные параметры CPU/RAM/environment; он не задаёт физические допуски. Один job исполняет один solver process; независимые jobs размещаются совместно. Continuation остаётся внутри научного выполнения.

**Удалить с прежней функцией:** AiiDA actors/WorkChains/ORM и Portal backend/frontend; Nix InstalledCode/release guards; custom image delivery, enrollment/admission/release state machines; старые multipart receivers и receipts; миграции input aliases и прежних checkpoints; дублируемые vendored schemas; initial-publication factory и неиспользуемые Deno wrappers. Новые formats можно выбрать без чтения старых `v2/v3/v4` массивов.

Writer, reader и fixtures нового формата меняются одним коммитом приложения. Формулы остаются в Core, научные критерии — в scientific code/постановке. GUI показывает результаты этих проверок; Ansible и OOD не становятся владельцами научной приёмки.

Свежая база важнее локального старого checkout. Кампания уже приняла [Core PR27](https://github.com/Afonenko-QCL-NEGF/QCLNEGF.jl/pull/27) и [Runner PR52](https://github.com/Afonenko-QCL-NEGF/QCLNEGFRunner.jl/pull/52): patch compatibility и прямой native Julia/Pkg путь. По [checkpoint #133](https://github.com/Afonenko-QCL-NEGF/qcl-negf/issues/133#issuecomment-6898137883) проверены standalone установка, CLI, малый solver и HDF5 readback. Это не свидетельство сходимости полной задачи. В новую базу переносятся эти и последующие принятые исправления, а не старое обязательное `=1.13.0`.

### Согласованное состояние Core и Runner

Очистка охватывает научный код, а не только инфраструктуру. При старте установить актуальные public entrypoints, реальные callers, tests и поддержку выбранных сценариев. Учитывать разные ветви: direct science main и поздний native5 implementation нельзя объединять целиком как один «latest». Нынешние ограничения из аудита — кандидаты для перепроверки, а не будущие факты.

Для основной поддерживаемой линии оставить один путь scientific input/resolver → execution → state writer/reader → analysis. Удалить ненужные дубли, deprecated compute/report wrappers, брошенные options/branches и private Core bridge там, где актуальный публичный API его заменяет. Нужное незавершённое соединение довести; ненужное удалить; научную идею сохранить в исследовательской заметке или явно отделённом эксперименте. Проверять реализации через extensions/adapters: пустое generic объявление само по себе не означает брошенный код.

Reference/optimized операторы, независимые oracles и научные варианты сохраняют собственные границы. Не удалять проверку из-за отсутствия сходимости и не ослаблять модель для завершения cleanup. Для checkpoint сохраняется согласованность actual problem/domain, U/G/Σ, mixer/history и counters; формат прежних receipts не обязателен.

CLI/help/examples должны совпадать с реально поддерживаемой линией. Отсутствующие действия явно обозначаются; stub/unknown-as-pass и скрытая подмена результата недопустимы. Первый научный инженерный сценарий проверяет реальное соединение input → solver → outputs → independent analysis; нужный для долгих runs pause/resume проверяется на том же пути. Наличие отдельных source APIs не заменяет этот результат.

## Julia, зависимости и обновление

У каждого worker остаётся постоянный локальный Julia depot. Подготовка среды через `Pkg.instantiate`/`Pkg.precompile` выполняется при установке или изменении среды; новый job использует готовые пакеты и кеш. Не создавать пустой depot для каждого задания и не переносить его вместе с результатами. Учётная запись исполнителя должна иметь доступ к своему постоянному кешу; временные аккаунты HTCondor при необходимости используют штатные слои depot. Pkg сам проверяет пригодность кеша. Разные CPU и ОС получают собственные локальные кеши, без общей фабрики sysimage. Новый процесс Julia всё ещё может компилировать недостающие специализации: отсутствие полной пересборки не означает нулевую стоимость старта. [Pkg depots](https://pkgdocs.julialang.org/v1/depots/), [Julia package images](https://docs.julialang.org/en/v1/devdocs/pkgimg/).

`Project.toml` задаёт поддерживаемые диапазоны, `Manifest.toml` — разрешённые зависимости конкретной среды. Начальная политика допускает разные patch-версии одной поддерживаемой Julia minor-серии; более широкую совместимость объявляем по мере проверки. Версии Git, Ansible и средств анализа также могут различаться в поддерживаемых пределах. Не вводить единый номер версии для всех инструментов. У запуска сохраняются фактическая версия Julia, Manifest, исходный commit либо переданный снимок кода, вход и JobID — обычные небольшие файлы рядом с результатом. Это запись условий опыта, а не отдельный протокол допуска к расчёту. [Pkg compatibility](https://pkgdocs.julialang.org/v1/compatibility/), [Project/Manifest](https://pkgdocs.julialang.org/v1/toml-files/).

Обновление — явное действие обслуживания. Текущие jobs заканчивают работу со своими исходниками и средой; новые получают подготовленную среду. Не выполнять `Pkg.update`, разрешение новых зависимостей или очистку используемого окружения внутри solver job. При редком повреждении кеша допускается его адресная очистка и повторная подготовка штатным Pkg. Собственный демон ремонта не нужен.

## Результаты и checkpoint

HTCondor переносит файлы и возобновляет исполнение; solver сохраняет и читает своё согласованное численное состояние. Очередь не умеет автоматически превратить память Julia в checkpoint. Для долгих runs предлагается штатный self-checkpointing: на безопасной границе итерации сохранить состояние, закрыть файлы и выйти с выделенным `checkpoint_exit_code`; HTCondor переносит `transfer_checkpoint_files` на submit node и перезапускает executable. Runner при старте обнаруживает checkpoint и продолжает расчёт. Это небольшой режим Runner и submit template, без собственного сервиса переноса. [HTCondor self-checkpointing](https://htcondor.readthedocs.io/en/26.0/users-manual/self-checkpointing-applications.html).

Начальный интервал — примерно час полезной работы, на ближайшей согласованной численной границе. После одного измерения стоимости записи, переноса и восстановления интервал можно изменить вручную. Штатный перенос этим способом означает новый процесс Julia и возможный JIT; это часть стоимости checkpoint. Локальная запись без выхода сама по себе не вызывает периодический off-host transfer. После внезапной потери worker восстановление возможно только с последнего уже перенесённого состояния.

Политика хранения небольшая:

- Лёгкая история residuals, наблюдаемых и logs пишется часто; построение графика не требует полного дампа состояния.
- Для восстановления держать последнее и предыдущее завершённые состояния. Новое сначала записывается во временное место, закрывается и публикуется атомарно; только затем удаляется лишнее старое. Сохраняется полный необходимый solver state, включая историю алгоритма, если она нужна для продолжения.
- Исходные массивы итогового результата, вход, среда и логи сохраняются для каждого опыта, в том числе несошедшегося. Новая попытка не затирает предыдущую. Удаление научных результатов — явное действие; временные файлы и лишние старые поколения checkpoint можно очищать автоматически после успешной записи.
- Каталог результатов на Proxmox и штатный HTCondor spool дают место для перенесённых файлов. Это не резервная копия от потери самого хранилища. При редком сбое перенос/перезапуск можно выполнить вручную; отдельная система автоматического восстановления не требуется.

В старом локальном Runner (`0c53c6d0f68e0b25fce79388db831da6fc3ae856`, `src/composition/scientific_execution.jl`, `checkpoint_request` и `durable_state`) full checkpoint мог запускаться по условию «wall time или каждые N SCBA», а также через snapshot. Поэтому заданные 1800 секунд не ограничивали частоту полных записей. В новом пути оставляем один понятный периодический триггер и явное сохранение при корректной остановке; прежний фиксированный byte budget и многослойные receipts не переносим. Фактический код кампании после её handoff может отличаться от этого локального снимка.

Возобновление проверяется на используемом научном пути: восстановленный расчёт должен продолжать ту же постановку и корректное состояние алгоритма. Перенос checkpoint на произвольную другую версию solver/Julia не обещается; смена среды при восстановлении остаётся явным решением исследователя.

### Дополнения после полной сверки

В научном приложении сохраняется потребность в конфигураторе template/form/YAML, редактировании структуры, отдельном bare-basis preview, справке по модели и объяснении actual inputs/defaults/overrides. Это отдельные функции; OOD adapter их автоматически не предоставляет. Первая удобная форма и порядок подключения выбираются по актуальным задачам при старте, без обязательного переноса старого Portal.

Минимальная карточка исследования — обычный файл с вопросом, постановкой, заметками, ссылками на runs и отчётом человека/агента. Сохранять отрицательные выводы и явно указывать использованные опыты. Развитый поиск, DB и собственное версионирование карточек не нужны для этого минимума. Справка и теория сохраняются как содержание, с локально читаемыми примерами; прежняя docs factory не переносится.

Исходные массивы и views сохраняют units/axes/weights, знаки, complex components, пропуски и причины отсутствия. Видны плановые, вычисленные, failed/skipped точки серии и история попыток. Read, явный derive и новый transport solve — разные действия; просмотр/сравнение не запускает скрытый SCBA/Poisson.

В Core сохраняются выбранная физическая модель, каналы рассеяния и полезные operator/spectrum/refinement studies. Compute chunking, адаптация energy window и inner numerical policy — разные механизмы; ни один не является скрытым способом сменить постановку ради RAM. Optional bare-bubble optics и пересчёт photon grid по полному состоянию учтены, но остаются за первым stationary transport этапом; lasing/power/dynamics не добавляются. GPU/distributed single-solve и document-only algorithms не становятся обещанными production возможностями.

Handoff научной кампании переносит актуальные code fixes, inputs, raw results, научные решения, различие baseline/variants и отрицательные результаты. Перенос одних PR без этого знания недостаточен. Его фактический состав устанавливается при старте/передаче, не по сегодняшнему checkpoint.

## Ресурсы и стоимость

Одна job на worker нужна для первого smoke, но не является конечной политикой. Целевой путь допускает несколько jobs, requests по обоснованным потребностям, использование свободного CPU и выбранную политику burst памяти. Владелец наблюдал около 30% выделенных job ядер при разных размерах задачи; причина не установлена.

Исторический общий расходуемый CPU grant удаляется. Учёт стоимости остаётся штатным: включая failed attempts, с различением queue wait, wall time, actual CPU time и allocated core-hours. Конечное поручение научной кампании задаёт её границы, без отдельного глобального quota engine в solver/приложении.

HTCondor partitionable slots возвращают завершённые allocations пулу данного worker. На Linux CPU shares допускают использование свободного CPU; custom cgroup cap можно отделить от reservation. Nomad имеет штатные `memory`/`memory_max` и остаётся сравнением при конкретном проигрыше HTCondor. Одновременные реальные пики выше RAM не становятся безопасными от наличия scheduler; Windows enforcement ещё не установлен. [HTCondor slots](https://htcondor.readthedocs.io/en/26.0/admin-manual/ep-policy-configuration.html), [custom cap](https://htcondor.readthedocs.io/en/26.0/admin-manual/configuration/starter.html), [Nomad resources](https://developer.hashicorp.com/nomad/docs/job-specification/resources).

После рабочего запуска нужен конечный опыт с одинаковой парой задач: последовательное и конкурентное выполнение, время всей пары, actual memory, CPU time, paging/I/O и сопоставимость результатов. Освободившиеся CPU могут обслужить готовые потоки, но штатная смена `JULIA_NUM_THREADS` не увеличивает работающий thread pool. Не строить новый phase/VM resource broker до измеренного проигрыша штатного размещения.

Тяжёлая локальная сборка получает выбранный хост после завершения его jobs; новые временно ждут. Остальные workers продолжают работу. CI/source preparation и deploy отделены от scientific job; package updates/GC не выполняются внутри расчёта, source и Manifest фиксированы на его срок.

Build не означает hot update. Замена общего исполняемого окружения/служб выполняется в согласованное обслуживание после завершения использующих его jobs. Новая zero-downtime rollout задача не вводится.

## Минимальные эксплуатационные правила

- Добавление/замена worker: private inventory, обычные accounts/trust, разрешённые CPU/RAM/scratch, Ansible и одна native job с outputs/cancel. Вывод — запрет новых jobs и завершение текущих. Для PVE Linux guest сохраняется штатный guest agent, без собственного транспорта.
- Настроить реальные права GUI user, Runner, depot, scratch и результатов. Проверить запись/чтение под фактическими пользователями; public/untrusted CI не получает production secrets. Административный доступ остаётся независимым от GUI приложения.
- Timeout submit/SSH/Ansible означает неизвестный исход: прочитать native очередь/VM/service состояние до повтора. Ручной сверки достаточно; новый delivery/reconciliation service не нужен.
- Проверенная cancel означает остановку payload, прекращение его повторов и освобождение allocation. Она не создаёт checkpoint и не удаляет сохранённые результаты.
- Использовать native disk request/free-space контроль и понятную причину hold/failure. При переполнении не затирать last-good checkpoint и не запускать бесконечный retry. Scientific data и технические logs имеют понятную владельцу retention.
- Новые inputs/results/config и нужный spool должны переживать обычную переустановку служб/ОС в согласованном persistent storage. На целевой машине явно выбрать простое резервное копирование либо зафиксировать отсутствие отдельной копии. Отмена backup старого QCL не распространяется на новые данные.
- Прежние SSD/root-grow/host-swap задачи отложены до фактической необходимости; они не являются скрытой частью очистки VM или условием первого job.

## Очистка сервера шире удаления VM

На целевом ноутбуке сначала получить один native live inventory: старый Intel Xeon PVE, actual VMID/config/status, диски/snapshots, shared storage и потребители. Составить точный список удалить/оставить. Старый OpenTofu state не заменяет этот список.

Проверить QCL остатки вне VM: host networking и QCL firewall rules; uploaded images/snippets/backup entries; disconnected volumes; старые GitHub runner registrations и queued releases; mounts, Nix cache trust/GC roots и локальный private site/state. Системные VG/thin pool, management bridge, общий `/var/lib/vz`, host swap и общие credentials не удаляются по одному имени QCL. Backup прежних научных данных не требуется.

В source storage/control имеют `protection` и `prevent_destroy`. Native destroy уничтожает принадлежащие VM volumes; отдельный data disk не является автоматической защитой. Удалять адресно подтверждённый QCL набор, затем проверять отсутствие выбранных объектов и сохранение машинного доступа. [Platform definition](https://github.com/Afonenko-QCL-NEGF/qcl-negf-platform/blob/6c5b11f3c74d44fed8b2c159f890b83e0b5456b9/tofu/proxmox/main.tf#L51), [Proxmox destroy](https://github.com/proxmox/pve-docs/blob/master/generated/qm.1-synopsis.adoc).

Локально найден ignored private site с inventory, access references и state; секретные значения не публиковались. Live список сервера в этой сессии не получен. Это ожидаемая граница планирования: фактические доступы устанавливает новая сессия на другом ноутбуке. Публичный пример inventory не выдаётся за действующие credentials.

## Процесс, инструкции и тесты очищаются вместе с продуктом

[PR132](https://github.com/Afonenko-QCL-NEGF/qcl-negf/pull/132) — полезная основа, но его 11 файлов не чистят README, component CONTRIBUTING, CI/tooling и все references навыков. Published PR и локальный dirty overlay различаются; повторно накладывать старый overlay нельзя.

Оставить один короткий процесс: вопрос/изменение → независимая опора → конечный различающий опыт или правка → результат → review существенного изменения. Codex остаётся средой. Sol/high ведёт работу; другой Sol/high проверяет существенное изменение по frozen ref и первичным свидетельствам; Sol/xhigh разбирает трудный конечный вопрос; Terra выполняет ограниченную механику. Роли используются по необходимости, без собственного dispatcher и вечных автономных циклов.

В AGENTS оставить только цель, текущий scope, source/dirty discipline, научную добросовестность, необходимость независимой проверки, выбор проверок по риску, сохранение машинных доступов и светлый UI. Убрать старые разрешения/VM роли/R00/P01–P32/CI-once/модельные расписания. Численные формулы, ports и mutable installation state не должны жить в AGENTS. Новое разрешение очистки не становится вечным разрешением удалять будущие результаты.

Четыре научных skills могут остаться короткими адресными справочниками. Их references обновляются вместе с кодом: старые multipart/200 MB/schema requirements и устаревшие telemetry symbols удаляются. Superpowers imports и конкурирующие процессы из старых документов исчезают из active path. Git history достаточно; отдельный огромный archive tree не нужен. Актуальная теория и литература сохраняются по содержанию.

Тесты удаляемого продукта удаляются вместе с ним. Содержательные operator/oracle, units/shapes, nonfinite, checkpoint и writer/reader проверки сохраняются. Убрать личные absolute-path assertions, literal version gates, snapshots внутренней module tree и проверки порядка команд старого release engine. Это не сокращение числа тестов ради числа.

Новый CI вызывает native инструменты. В рабочем цикле — затронутое свойство; перед merge — нужные связи; инфраструктурный smoke — при изменении infrastructure. Обычный научный импорт не требует Nix, Deno, сборки документации и платформенных tests. Root package factory и общий semver не переносятся в новую обёртку.

## Последовательность исполнения

1. На доступном ноутбуке подготовить чистую ветку с актуальными входными инструкциями и минимальной lab config, без старого dirty overlay и автоматического продолжения прежних программ. Снять свежие refs/dirty state, учесть текущий статус научной сессии и обновить изменившиеся участки функциональной карты. Выбрать поддерживаемые научные сценарии; cleanup Core/Runner и перенос их кода ждёт handoff/согласования владения, инфраструктура независима. Собрать private live inventory и машинные access references. Отделить кампанию и foreign resources. Установить finite бюджет инженерного пилота. До очистки проверить практический установочный путь HTCondor на CachyOS host и готовые пакеты Linux guest. Новая собственная package factory не является допустимым автоматическим продолжением.
2. Очистить подтверждённый старый QCL на PVE и внешние QCL remnants, сохранив административный доступ. Без старого data restore и совместимого runtime.
3. Поднять один Linux guest и HTCondor pool с worker непосредственно на CachyOS host. Коротким инженерным payload проверить job, outputs, cancel и совместное размещение. Затем GUI submit/status/cancel к той же очереди, графики actual ресурсов и действующие машинные протоколы доступа. Это инженерная проверка; научный QCL путь подключается после переноса приложения и не принимается по этому smoke.
4. После handoff научной кампании по фактическому свежему коду привести Core/Runner к согласованному поддерживаемому состоянию и собрать приложение. Проверить один реальный научный input→solver→output→independent-analysis путь, не подменяя его synthetic fixtures. Сохранить полезные функции/идеи и исходники кампании по карте; убрать брошенные ветви и дубли, старые components/gitlinks/tooling/instructions/tests. Закрыть superseded PR/issues, вывести ненужные repos после переноса нужного содержимого.
5. На актуальном приложении выполнить конечное сравнение одной и той же пары научных задач последовательно/конкурентно. Затем проверить recovery/offline/checkpoint и обслуживание, необходимые для долгих runs; не делать полную fault matrix условием первого job.
6. Подключить Windows VM native и проверить OS adapter, launcher и доступные протоколы. Linux путь продолжает работать независимо от этой квалификации.
