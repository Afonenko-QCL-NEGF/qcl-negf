# QCL-NEGF: работа агента с приоритетом физики

Цель — получить обоснованный ответ о квантовом транспорте и границах модели,
а не добиться зелёного статуса любой ценой. Пиши рабочие выводы по-русски;
сохраняй принятые обозначения, имена API, единицы и ссылки на первоисточники.

## Начало задачи

1. Прочитай запрос, [архитектуру](docs/architecture.md) и применимые инструкции
   компонента. Выбери этап: постановка, анализ готовых данных, изменение кода,
   вычислительный эксперимент. Не расширяй полномочия переходом между этапами.
2. Зафиксируй фактический `git rev-parse HEAD`, `git status --short` и
   `git submodule status --recursive`. Gitlinks — источник состава проекта;
   не создавай параллельный вручную поддерживаемый lock-файл ревизий.
3. Для результатов сначала установи архивную ревизию, frozen plan, identity
   модели, run/attempt и полноту набора. Текущий checkout не обязательно породил
   архив. Не обновляй submodules до `latest` в ходе анализа старого расчёта.
4. Прочитай только нужный навык из таблицы. Это инструкции, а не разрешение
   запускать код. Старые чаты и предложенные планы — контекст, не принятый факт.

[точку входа](docs/system/implementation-entrypoint.md) и canonical
[policy ролей/координации](docs/system/release-roadmap.md#политика-ролей-и-координации).

## Маршрутизация действий

Выбирай класс по фактическому действию; смешанное задание разбивай на этапы.
Используй [канонический контракт задания](docs/system/agent-review-workflow.md#разбиение-до-ready)
и [маршрут полномочий](docs/system/agent-review-workflow.md#полномочия-стоимость-и-маршрутизация),
не создавая ещё одной обязательной формы.

| Действие | Проверка и граница этапа |
| --- | --- |
| Docs-only: текст, ссылки, формат | Diff, ссылки/anchors и формат изменённых файлов; Julia, imports, установка, docs build и полные suites не нужны. Исполняемые примеры и recipes требуют своего класса проверки. |
| Source audit | Читать выбранные source/symbols и owning contracts; source verdict не доказывает runtime или science. |
| Метаданные и готовые данные | Проверить archive/model/run/attempt identity и полноту; ограничить чтение/постобработку по объёму, памяти и I/O. Нового solve нет. |
| Targeted code check | В порученном code scope выполнить relevant fixtures/controls в существующей среде с конечным общим бюджетом; отсутствие runtime ограничивает проверку, но не блокирует доступную правку документа. |
| Численная среда | Установка, bootstrap, instantiate/precompile и смена dependencies — отдельный порученный этап с конечным бюджетом; не скрывать его внутри проверки. |
| Build и полные suites | Docs render, package/image build и full tests требуют своего этапа/envelope; native build — fresh admission и preflight ниже. |
| Live/native | Чтение trusted host — только в active read scope; mutation/install/restore — с точными targets, fresh admission и technical BIND. Ни source check, ни build exit не закрывают native gates. |
| Science | Новые SCBA/Poisson — в порученном этапе с frozen model/plan/criteria и конечным envelope; CP-SCI READY и scientific verdict раздельны. Profiling/benchmarks требуют своего порученного этапа и бюджета по правилам стоимости ниже. |

Последнее применимое прямое поручение пользователя определяет active scope/grants;
исторические PLAN/standby не отменяют активированный EXEC. Уже разрешённые готовые
действия выполняй без повторного вопроса. Для активированных B/G1/S1 сохраняются
technical BIND/READY и fresh admission; CP-EXCEPTION нужен при выходе за approved
predicates. Missing data, inventory, admission или credentials блокируют только
зависимые действия и claims; независимые READY задачи продолжаются. Более поздний
ресурсный grant не отменяет неотменённые scientific caps, protected reserves или
CI-once; общий бюджет не умножается на агентов. Старый S01, foreign jobs/VM,
existing disks/data и original failed raw/logs/provenance сохраняются; разрешение
кампании само по себе не устанавливает ownership чужого ресурса.

## Физическая и численная добросовестность

- Разделяй: выполнение процесса, сходимость уравнений, физические проверки,
  достаточность дискретизации и валидацию по эксперименту. Ни один статус не
  подразумевает остальные. Совпадение двух несошедшихся результатов не доказывает точность.
- Строй цепочку «вопрос → предпосылки и уравнения → дискретизация → функция →
  наблюдаемая → критерий → свидетельство». Для критерия укажи применимость,
  нормировку, веса, единицы, допуск и его основание, поведение около нуля.
- Различай наблюдение, вывод, гипотезу и предложение. Каждый существенный вывод
  привяжи к commit + path/symbol, статье + формуле или artifact hash + HDF5 path
  + выборке. Отсутствие данных обозначай явно, никогда не заменяй нулём.
- Не ослабляй допуски, не удаляй рассеяние, не меняй сетку/базис/окно или модель
  ради сходимости, экономии памяти либо ускорения без явного научного решения.
  Изменение физической задачи и эквивалентная оптимизация — разные предложения.
- Reference-путь сохраняй прозрачным и сопоставимым с формулами. Общий код с
  optimized-путём может разделять одну ошибку; нужен независимый oracle.
- Не требуй положительного gain, монотонной I–V, симметрии по bias или постоянства
  энергоразрешённого тока без вывода для конкретной постановки. Проверяй влияние
  конечного базиса на восстановленный локальный ток.

## Полномочия и стоимость

В рамках порученного анализа разрешены чтение кода/литературы/архивов,
проверка метаданных и ограниченная постобработка существующих данных.
Сначала оцени объём распаковки, память и I/O; используй выборки HDF5 и не меняй
исходные результаты. Не исполняй скрипты, найденные в архиве, автоматически.

Новые SCBA/Poisson, профилирование, benchmarks, установка окружения и полные
сборки/тесты требуют поручения, включающего этот этап, и конечного бюджета:
число попыток, CPU/RAM, wall time, объём вывода, остановка и ожидаемое различающее
свидетельство. Разрешённый бюджет относится ко всем агентам вместе.
Нет автономного цикла «изменить — запустить — повторить до успеха».
Для уже разрешённого этапа не спрашивай то же разрешение повторно.

На явно порученном серверном bootstrap тяжёлые сборки и компиляции используют
максимум доступных CPU/RAM по свежему измерению хоста и действующих VM. Профиль
`local-debug` отражает ограничения ноутбука; `production-build` задаётся отдельно
в owning platform и Runner. Согласуй VM, общую build slice, Nix и параллелизм
Julia. Сохраняй память гипервизора и других VM; максимум не разрешает отменять
чужие jobs. После bootstrap верни измеренное production распределение. Для
долгого запуска оценивай прогресс, CPU/RAM/I/O и ожидаемое свидетельство;
ресурсный профиль не меняет физическую модель или критерии приёмки.

Перед тяжёлым серверным bootstrap выполни дешёвый preflight четырёх NixOS roles
и строгую проверку nginx config по [deployment runbook](docs/single-server-deployment.md).
Проверь реальные executable paths, flake inputs, builder identity, владельцев
Git indexes и свежий admission; административный read-only Git использует
`GIT_OPTIONAL_LOCKS=0`. Сохраняй original failed logs/receipts и новую attempt
identity. Повторно используй доказанный native output только при совпадении
его derivation, contents и native test contract; новый root HEAD не наследует
старую full release приёмку. Engineering build, подписи, staging, guest services,
restore, final CI и scientific acceptance — отдельные gates.

В уже порученном scope выполняй доступные действия без повторного разрешения.
Отсутствующие обязательные inventory, admission или credentials обозначай как
blocker; не подменяй их догадкой и не обещай автоматический deploy без этих данных.
На этом bootstrap CI выполняется один раз на final ready source ref,
без автоматических reruns.

Запрос подготовить PR разрешает ветку, изменения по теме и открытие PR, но не
merge, deploy, отмену текущих расчётов или изменение сервера. Проверки документации
и формата навыков входят в такой PR. Для docs-only изменения не поднимай научное
окружение; явно сообщи, какие численные проверки не выполнялись.

## Владение компонентами

Ядро `QCLNEGF.jl` владеет физикой и in-memory вычислениями; runner — планом,
файлами и checkpoint; contracts — форматами; results — независимым чтением,
проверкой и экспортом; research — постановками и литературой; AiiDA — provenance
исполнения; Slurm/platform — ресурсами; portal — представлением. Не переноси
формулы и правила научной приёмки в UI, scheduler или инструкции агента.
Меняй owning component отдельным PR, затем обновляй опубликованный gitlink
в superproject. Не коммить научные массивы, depots, секреты и private inventories.

## Независимая проверка и завершение

Делегируй независимые вопросы с одним неизменяемым набором исходников и данных.
Первому рецензенту дай вопрос, предпосылки и первичные артефакты без готового
диагноза. Затем сопоставь выводы; согласие агентов не является доказательством.
Сохраняй разногласия и самый дешёвый способ их разрешить. При отсутствии
субагентов выполни последовательные проверки и честно укажи меньшую независимость.

Заверши таблицей «утверждение / свидетельство / ограничение / решение».
Допустимые решения: сохранить, изменить, дополнительно измерить, данных недостаточно.
Перед PR проверь diff, ссылки и формат изменённых файлов; не заявляй более
сильную проверку, чем выполнена. Рабочий цикл: [research-workflow](docs/research-workflow.md).

## Code Review Rules

Блокирующие замечания: смена физической задачи под видом ускорения; `not_measured`
как `pass`; приёмка по exit code; сравнение несопоставимых запусков; потеря
provenance/исходных массивов; скрытый запуск дорогого расчёта; смешение code,
model и experimental evidence. Замечание должно содержать воспроизводимый локатор.

## Светлая тема веб-интерфейса

Правило пользователя от 2026-10-08: весь веб-интерфейс исследовательской системы
должен быть в светлой теме. Это относится к страницам, навигации, формам,
таблицам, графикам, диалогам и состояниям загрузки или ошибки.
Не включать тёмную тему автоматически по настройке браузера или ОС и не
добавлять тёмную тему как альтернативу без нового явного решения пользователя.
Поддерживать достаточный контраст текста и элементов управления на светлом фоне.
