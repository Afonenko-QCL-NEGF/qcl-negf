# QCL-NEGF: простой научный и инженерный рабочий процесс

Цель — обоснованная физика, понятный код и удобные готовые инструменты.
Рабочие выводы и новые документы пиши по-русски; сохраняй единицы, API и первоисточники.

## Текущий этап

Для переработки кластера сначала прочитай
[точку входа](docs/implementation/cluster-execution-2026-11-15.md),
[план](docs/implementation/clean-start-plan-2026-11-15.md) и нужные части
[карты функций](docs/implementation/functional-reassessment-2026-11-15.md).
Публикация документов не запускает работы; исполнение начинается ручным поручением пользователя.

Приоритет: последнее поручение пользователя → новая точка входа и план → актуальные
научные договоры затронутого кода. Старые R00/P01–P32, Superpowers, расписания,
bootstrap grants, CI-once, release/deployment программы и правила сохранения старых
данных не управляют этим этапом. Старые README, architecture, component instructions
и SKILL.md изучаются по необходимости; их устаревшие требования процесса пересматриваются.
Формулы, единицы, независимые oracles и научная добросовестность сохраняются.

## Начало и границы

- Сними фактические HEAD, status и recursive submodule status. Сохраняй чужие
  изменения и отдельные рабочие деревья. Ветка плана не задаёт окончательную
  научную композицию; актуальные Core/Runner и handoff кампании133 устанавливаются
  при старте и перед переносом научного кода.
- Пока научная сессия меняет код, готовь инфраструктуру независимо. Cleanup и
  перенос её кода выполняй после передачи работы либо согласования владения.
- Разрешения и конечный этап задаёт ручной старт. Выполняй уже разрешённое без
  повторных запросов; неизвестное владение блокирует только конкретное опасное действие.
- Прежний QCL можно очистить в согласованных границах. Proxmox, чужие VM/storage,
  машинные credentials и независимая научная машина/новые результаты сохраняются.
  Новые данные не получают пожизненное разрешение на удаление по старому cleanup.
- Не коммить секреты, private inventories, научные массивы, depots и runtime state.

## Физика и целостный код

- Разделяй process completion, сходимость, физические проверки, дискретизацию и
  экспериментальную валидацию. Unknown/not_measured не становятся pass или нулём.
- Связывай существенные выводы с предпосылкой/формулой, функцией на конкретной
  ревизии или исходными данными. Невязка уравнения отличается от смешанного шага.
- Инженерная переработка не разрешает скрыто менять модель, scattering, сетки,
  базис, окно или допуски. Научный вариант требует отдельной явной постановки.
- Сохраняй независимые reference/oracle и численное состояние восстановления.
  Дубли, брошенные ветви, stubs и неподдерживаемые обещания очищай по свежему коду.
  Generic declaration с реализацией через extension/adapter не является заглушкой.
- Core владеет физикой и in-memory состоянием; Runner — входами, выполнением и
  файлами; analysis — независимым чтением; UI представляет их результаты.
  Поддерживаемый путь проверяется целиком от input до scientific output/report.

## Простота, проверка и роли

- Используй HTCondor, Julia Pkg, системные пакеты и Ansible. VM описывай OpenTofu.
  По умолчанию принимай системную версию инструмента; при её отсутствии ставь
  актуальную стабильную upstream. Не вводи exact version pins или hash-допуски. Для редких сбоев
  допустима ручная сверка. Не создавай собственный scheduler, package manager,
  SHA-допуск, receipt/reconciliation framework или постоянный agent dispatcher.
- Один Sol/high ведёт задачу; другой Sol/high независимо проверяет существенные
  изменения; Sol/xhigh получает конечный трудный вопрос; Terra — ограниченную
  механику с проверкой ведущего. Используй штатных subagents по необходимости.
- Рецензент проверяет первичные входы и результат, а также необходимость нового
  слоя для пользовательского сценария. Согласие агентов не заменяет проверку.
- Проверяй затронутое поведение, реальные producer/consumer связи и существенные
  отрицательные случаи. Неизменные проверки повторяй при новом основании.
  Docs-only не требует научной среды; тесты формы/версии оправдываются поддерживаемым договором.
- Перед тяжёлой операцией выбери ресурсы после host reserves, конечный timeout,
  объём вывода и сохранение/остановку. Общий этап включает всех агентов.
  Не строй систему учёта ради этих ограничений.
- При timeout удалённой операции сначала прочитай native состояние до повтора.
  Сохраняй первичную ошибку. Короткую задачу завершай кратким результатом;
  для научного вывода укажи свидетельство и ограничения.

Все web UI, графики и состояния ошибки/загрузки — в светлой теме с достаточным
контрастом. Тёмная тема и автоматическое переключение по ОС не добавляются.
