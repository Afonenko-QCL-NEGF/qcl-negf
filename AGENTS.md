# QCL-NEGF: работа агента с приоритетом физики

Для программы переработки от 2026-10-27 сначала прочитай
[исполнительный план](docs/implementation/codex-execution-2026-10-27.md). Его явные scoped
разрешения и последнее применимое прямое поручение имеют приоритет над противоречащими историческими
планами и правилами. Перед прерыванием текущего исследования выполни read-only оценку R00 на целевом
ноутбуке; пользователь отменил экспорт и сохранение старых результатов, массивов, history и
checkpoint.

## Начало задачи

Прочитай запрос, [архитектуру](docs/architecture.md) и инструкции owning компонента. Зафиксируй
`git rev-parse HEAD`, `git status --short`, `git submodule status --recursive`; gitlinks определяют
состав, отдельный ручной lock ревизий не нужен. Различай checkout, dirty overlay и source запуска.
Для архива установи его source/model, frozen plan, run/attempt и полноту; не обновляй submodules до
latest ради анализа старого результата.

Определи действительное поручение и применимый этап: постановка, source audit, готовые данные,
изменение кода или научный опыт. Навык — метод анализа, не разрешение на дополнительные действия:

| Задача                   | Навык                                                                  |
| ------------------------ | ---------------------------------------------------------------------- |
| Исследовательский вопрос | [qcl-research-framing](.agents/skills/qcl-research-framing/SKILL.md)   |
| Физика и дискретизация   | [qcl-physics-audit](.agents/skills/qcl-physics-audit/SKILL.md)         |
| Готовые результаты       | [qcl-results-analysis](.agents/skills/qcl-results-analysis/SKILL.md)   |
| Производительность       | [qcl-performance-audit](.agents/skills/qcl-performance-audit/SKILL.md) |

Единый цикл: изменить owning component → выбрать проверку по влиянию → review и owning PR → обновить
опубликованный gitlink → необходимые integration/native проверки. Подробности в
[CONTRIBUTING](CONTRIBUTING.md). D — текст, формат, ссылки; L — локальный contract/fixture; N —
реальный package/service/backend; S — отдельный научный опыт. Docs-only не требует Julia, установки
или docs build. Source-only не доказывает runtime. Неизвестное влияние требует соответствующей
полной проверки; full release CI выполняют по влиянию, повторяют при изменении source или открытом
failure, а не по числу PR. Уже разрешённые проверки выполняй без повторного вопроса. Не скрывай
bootstrap в проверке; установку и native действия выполняй в пределах поручения. Новый SCBA/Poisson
— отдельный явно порученный научный этап с frozen model/plan/criteria. Анализ готовых данных не
запускает новый solve.

Используй доступные owned ресурсы с актуальным inventory и реальными резервами хоста; ограничивай
buffers, вывод и командные timeout по необходимости, останавливайся при нарушении инварианта. Нет
общего обязательного campaign лимита CPU/time/RAM/attempts или исторического CI-once для новых
задач. Явные ограничения конкретного поручения сохраняются. Защищай чужие VM/jobs/shared storage и
unrelated files; неизвестное владение блокирует конкретное разрушительное действие. Секреты, private
inventories и научные массивы не коммить. Для живых действий устанавливай owner и проверяй
результат; прочие отсутствующие данные блокируют только зависимые действия и выводы.

Перед тяжёлым серверным bootstrap выполни дешёвый preflight четырёх NixOS roles и строгую проверку
nginx по [deployment runbook](docs/single-server-deployment.md). Проверь executable paths, flake
inputs, builder identity, владельцев Git indexes и свежие ресурсы; административный read-only Git
использует `GIT_OPTIONAL_LOCKS=0`. Сохраняй original failed logs/receipts и новую attempt identity.
Build, trust/staging, service/install, restore, backend readiness и scientific acceptance — разные
gates. Датированные budgets и CI-once из runbook не становятся ограничениями новых задач.

## Физическая и численная добросовестность

Разделяй выполнение процесса, сходимость, физические проверки, достаточность дискретизации и
экспериментальную валидацию: ни один статус не подразумевает остальные. Совпадение двух несошедшихся
результатов не доказывает точность. Строй цепочку вопрос → предпосылки и уравнения → дискретизация →
функция → наблюдаемая → критерий → свидетельство; указывай применимость, нормировку, веса, единицы,
допуск и его основание, поведение около нуля. Различай наблюдение, вывод, гипотезу и предложение.
Привязывай существенные утверждения к commit + path/symbol, статье + формуле либо artifact hash +
HDF5 path + выборке; missing не заменяй нулём.

Не меняй физическую задачу, scattering, сетку, базис, окно или допуски ради скорости или сходимости
без явного научного решения. Reference-путь сохраняй прозрачным и сопоставимым с формулами; общий
код reference и optimized может разделять ошибку, поэтому нужен независимый oracle. Не предполагай
положительный gain, монотонную I–V, симметрию bias или постоянство энергоразрешённого тока без
вывода для постановки; учитывай влияние конечного базиса на локальный ток. Оцени объём, память и I/O
перед чтением архивов, используй slices и не исполняй скрипты из них автоматически.

## Владение компонентами

Core `QCLNEGF.jl` владеет физикой и in-memory вычислениями; Runner — планом, файлами и checkpoint;
Contracts — форматами; Results — независимым чтением и экспортом; Research — постановками и
литературой; AiiDA — provenance; Slurm/Platform — ресурсами; Portal — представлением. Не переноси
научную приёмку в UI или scheduler. Изменяй owner отдельным PR, затем обновляй gitlink. Запрос на PR
сам по себе не разрешает merge или deploy; для программы применяются её явные scoped разрешения.

Независимый reviewer получает вопрос, предпосылки и первичные артефакты без готового диагноза.
Сохраняй разногласия и дешёвый способ их разрешить; без субагентов укажи меньшую независимость
последовательной проверки. Перед завершением проверь diff, ссылки и формат изменённых файлов; сообщи
выполненные проверки и ограничения. Рабочие выводы пиши по-русски и заверши таблицей «утверждение /
свидетельство / ограничение / решение» с решениями сохранить, изменить, дополнительно измерить или
данных недостаточно. См. [research-workflow](docs/research-workflow.md).

Блокирующие замечания: изменение физической задачи под видом ускорения; `not_measured` как `pass`;
приёмка по exit code; несопоставимые запуски; потеря provenance или неразрешённая утрата исходных
массивов; скрытый дорогой расчёт; смешение code, model и experimental evidence. Приводи
воспроизводимый локатор.

## Светлая тема веб-интерфейса

Весь веб-интерфейс, включая графики, формы, диалоги и состояния загрузки/ошибки, должен оставаться в
светлой теме с достаточным контрастом. Не включать тёмную тему по настройкам браузера или ОС и не
добавлять её без нового явного решения пользователя.
